# 運転免許証の有効期限の管理（gas/License.gs・版 2026-11-18c）

- 作成：2026-11-16。ブランチ feature/notification-settings。**本番未導入**（Apps Script・スクリプトプロパティ・トリガー・デプロイは変更していません）。
- 目的：運転免許証を持つ全従業員（正社員・アルバイト）の有効期限を、人の確認なしで管理する。人が対応するのは「免許の有無」の初回入力と例外（期限切れで報告がない・「その他」の期限・要確認）だけ。
- 本番へ入れるときは LICENSE_MODE を**未設定（off）のまま**入れます。off のあいだは、毎朝の処理も LINE の受け口も今までと同じ動きです。
- 版 2026-11-16c（11/17）：送る範囲 LICENSE_SCOPE を追加。まず管理本部の人だけで本番テストするため（5-2・6-2）。
- 版 2026-11-17a（11/17）：1回の登録・更新で送られた写真（表・裏など）をすべて残す。登録のお願い（E-80）の文面を変更（4・6-3）。本番テストで、表→裏の2枚を続けて送ると表がゴミ箱へ移ったため。
- 版 2026-11-17b（11/17・17a は本番未導入のまま 17b にまとめた）：催促（E-81）を登録のお願いと同じ調子の文に、期限のお知らせ（E-82〜E-85）の宛名を外して「お疲れさまです。管理本部です。」から始める文に、写真の受付の返信（E-86）を「表面と裏面の写真を」に。
- 版 2026-11-17c（11/17・17a・17b は本番未導入のまま 17c にまとめた）：登録・更新のお礼（E-89・E-90）の宛名を外し、「お疲れさまです。管理本部です。」から始める文に。本人あての文に宛名は無くなった。
- 版 2026-11-18a（11/17 作成・**本番未導入**）：写真を AI（Claude API）で確認する（LICENSE_AI_CHECK）。on では、読めない写真は保存せずに再送をお願いし、表面から読み取った有効期限をそのまま記録する（本人に期限を選ばせない）。最初は **LICENSE_AI_CHECK を未設定（off）のまま**入れる（今までと同じ動き）。調査の結果は 1-6・1-7、仕様は 4-2、反映は 6-4。
- 版 2026-11-18b（11/17 作成・**本番未導入**。本番は 18a・LICENSE_AI_CHECK=on）：写真の受付を「表面 → 裏面」の1枚ずつの案内にした（受付の文 E-86 を「まず表面の写真を」に。表面では期限を記録して「続けて、裏面の写真を」だけ、お礼は裏面のあとに1回。表・裏を一緒に送っても返すのは1通）。表面だけで裏面が届かなければ翌朝に1回お願いする。前と同じ期限の再登録を要確認にしない不具合の修正。仕様は 4-2、反映は 6-5。
- 版 2026-11-18c（11/18 作成・**本番未導入**。本番は 18b・Webアプリ v40）：受付のエラーを「免許証お知らせ記録」と「通知送信履歴」に残し（段階・要約）、安藤さんの個別 LINE へすぐ送る（朝のまとめ ADMIN_NOTIFY=digest を通さない。同じ人・同じ日・同じエラーは1回）。写真の取り出しの一時的な失敗は最大2回やり直す。LINE の外の画像（external）は originalContentUrl から取り出す。調査は 1-8、反映は 6-6。

## 1. 調査の結果（実装の前に確認したこと）

### 1-6. doPost の中で AI を呼ぶと返信が遅れる件（版 2026-11-18a の前に調べたこと）

- **LINE の返信トークン**：公式の資料（Messaging API の「メッセージを受信する」「メッセージを送信する」）では、返信トークンに使える時間の秒数を、今回読めたページでは確かめられませんでした。秒数は変わることもあるため、余裕を見て **受け取ってから45秒を過ぎたら返信ではなくプッシュで送る**ことにしました。返信に失敗したときもプッシュで送ります。
- **Webhook の応答と再送**：LINE は「Webhook の出来事は非同期で処理することを勧める」としています。Apps Script の doPost は、処理が全部終わってから応答を返すため、AI の確認の数秒がそのまま応答の遅れになります。LINE の管理画面で「Webhook の再送」をオンにしていて、2xx が返らなかったときは、同じ出来事（同じ webhookEventId）がもう一度届きます。
- **とった対策**（受け取り → AI で確認 → 保存 → 返信、の形）
  1. 出来事の印（webhookEventId）を、処理の**前**に付ける（処理中に届いた再送を二重に扱わない）。
  2. AI の確認は**ロックの外**で行う。保存・番号・タブの更新だけをロックの中で行う（AI を待つ間、ほかの LINE の処理（問い合わせ・社員番号の登録など）を待たせない）。
  3. 待っている間、本人のトークに「…」（LINE の読み込み中の表示）を出す。
  4. 時間がかかったとき・返信に失敗したときはプッシュで送る（上）。
  5. 読めない写真は、保存する前に AI で確かめるので、**一度もドライブに置かない**。前の回の写真も消さない。
- **採らなかった形**：受け取ってすぐ保存して返信し、時間主導のトリガーで AI を確認してプッシュで返す形。Apps Script のトリガーは最短1分ごとのため本人が1分以上待つことになり、結果をすべてプッシュ（月の送信数に数える）で送ることになるため。
- AI の応答時間は、実際の API を呼んでいないので測っていません（本番の record で、ログの時刻から確かめられます）。

### 1-8. 社員番号10085 の「写真をうまく受け取れませんでした」と、管理者へ届かなかったエラー（版 2026-11-18c の前に調べたこと）

**(1) AC_adminNotice_ の送り先と、送られない条件（本番のコード.gs 2026-11-17e）**
- AC_adminNotice_(種類, 文) は、ユーザープロパティ `sent:今日:notice:種類` があれば送りません（**種類ごとに1日1回**。人は区別しない）。無ければ AC_pushLine_ を呼びます。
- 17e の AC_pushLine_ は、スクリプトプロパティ **ADMIN_NOTIFY=digest のとき、管理者の個別 LINE へは送らず「朝のまとめ」にためます**（AC_digestAdd_）。まとめは平日の朝（問い合わせのまとめ 9:00 の回）に**勤怠管理グループへ**送られ、土日祝は送られません。17e の CHANGELOG にも「免許証の要確認・各種エラーなど」をまとめに入れると書かれています。
- そのため、ADMIN_NOTIFY=digest のときは、免許証のエラー（【エラー】運転免許証の写真を保存できませんでした…）は**安藤さんの個別 LINE には届かず**、次の平日の朝に勤怠管理グループのまとめに入ります（まとめが送られるまでは、どこにも届きません）。本番の ADMIN_NOTIFY の値はこちらでは確かめていません（プロパティは見ない）。設定されていれば、これが届かなかった理由です。
- 設定されていなかった場合でも、同じ日にほかの人の写真のエラー（種類 license-photo）を先に1回送っていれば、その日の2回目からは送りません。
- お知らせ設定（従業員ごとの「受け取らない」）は、管理者へのお知らせには使われていません（AC_pushTo_ は設定を見ない）。
- **通知送信履歴**には、AC_adminNotice_ は何も書きません（書くのは毎朝の処理など、呼び出し側が AC_noticeLog_ を呼ぶときだけ）。免許証の受付のエラーはどこにも記録が残らない作りでした。
- Logger.log の内容は、Webアプリ（doPost）の実行では「実行数」の画面で見られないことがあります。原因を後から追えるよう、記録はシートに残すことにしました。

**(2) LINE の画像の取り出し（Get content）で 200 以外になりうる場合**（LINE の公式資料。Messaging API リファレンスと「メッセージを受信する」）
- 202：動画・音声の大きなファイルで、準備が終わっていないとき（資料は動画・音声に結びつけて書いており、画像で返るかどうかは書かれていない）。準備の状況を確かめる transcoding の API は動画・音声だけ（画像は 400）。
- 404：メッセージ ID が無いとき。送られた中身は「一定の期間で自動で消える。どれだけ残るかの保証はない」。
- 410：本人が送信を取り消したとき。
- 5xx：Get content の項には書かれていない（共通の表に 500「内部のエラー」）。429 は送りすぎ。
- **contentProvider.type が external**：画像が LINE の外にあるとき。資料は「外部のときは Get content で取り出せない」とし、URL は contentProvider.originalContentUrl に入る。18b までは、この場合も Get content を呼んでいたため、**毎回失敗していたはず**です（届いたのが external だったかは、記録が無く確かめられません）。
- **imageSet**（一緒に送った写真）：1枚ずつ別のメッセージ ID で、それぞれ取り出せます。Webhook は imageSet.index の順とは限らない順で届きます。古い Android の LINE（11.15 以前）からだと index・total が付きません（18b は total が無ければ1枚ずつ返すので、案内が重なることはあっても、失敗にはならない）。
- 利用者が送る中身の大きさの上限は、資料に書かれていません。

**(3) LIC_onPhoto_ が「写真」として扱うメッセージ**
- LIC_eventKind は、message.type が **image** で、その人が受付中のときだけを「写真」とします。file（ファイルとして送った画像）・video などは免許証の処理には入らず、今までどおり問い合わせに回ります。紛れ込みはありません（file で送った人は「写真をうまく受け取れませんでした」にはならず、問い合わせになります）。

**(4) 10085 の人だけが失敗する理由の候補**（記録が無いため特定はできていません）
- 「写真をうまく受け取れませんでした」は、①取り出しの失敗、②ドライブへの保存の失敗、③受付の処理のどこかでの予期しないエラー（ロックの待ち時間切れ・シートの読み書きなど）の3か所で返していました。どれかは区別されていませんでした。
- 1人だけ毎回失敗するなら、その人の写真の送り方による①がいちばん考えられます（LINE の外の画像（external）・取り出しの一時的な失敗が続いた、など）。②③は、ほかの8人が同じ時期に成功しているので考えにくいです。
- 版 2026-11-18c で、次に失敗したときは「免許証お知らせ記録」に段階（取り出し／AI／保存／記録／返信／受付）とエラーの要約（HTTP の番号・何回試したか）が残ります。

### 1-7. LINE から受け取る写真の大きさと、AI へ送る前の縮小

- LINE の資料には、利用者が送る画像の大きさの記載がありません。LINE のアプリは送るときにふつう圧縮します（原寸で送る設定にすると大きくなります）。
- Claude API の上限（公式の資料）：1枚あたり base64 で 10MB、縦横 8000px まで。Claude Sonnet 5.5 などの新しいモデルは、長い辺 2,576px・4,784 トークンを超える画像を自動で縮小してから読みます。
- **縮小はしません**。Apps Script には画像を縮小する機能が無く、API 側が自動で縮小するためです。base64 で 10MB を超えないよう、**7MB を超える写真は AI へ送らず**、AI が使えないときと同じ扱い（ボタン・要確認）にします。
- 費用の目安：写真1枚は最大で約4,800トークン（Sonnet 5.5 は入力100万トークンあたり2ドル）。指示と応答を合わせても1枚あたり約1〜2円。上限 LICENSE_AI_DAILY_MAX（既定200枚）でも1日数百円までです。

### 1-1. doPost が今、画像・テキスト・postback をどう処理しているか

本番の「コード.gs」（gas/AlcoholCheck.gs）の `doPost` → `AC_handleEvent_` の流れです。

| 出来事 | 今の処理 |
|---|---|
| グループ・複数人トーク | `AC_handleGroupEvent_`：参加・退出、postback（`sch|` は TOT 反映、それ以外は問い合わせのボタン）、「部門登録 ○○」だけ。ふだんの会話には反応しない |
| 1対1・友だち追加（follow） | お礼と社員番号のお願い（E-13） |
| 1対1・テキストで社員番号だけ（4〜6桁） | 従業員登録（E-14〜E-16、管理者へ A-31） |
| 1対1・それ以外のテキスト | 問い合わせ（`INQ_onUserEvent_`・gas/Inquiry.gs） |
| 1対1・画像・スタンプ・動画など（テキスト以外のメッセージ） | 問い合わせ（`INQ_onUserEvent_`） |
| 1対1・postback | 問い合わせ（`INQ_onUserEvent_` → `INQ_onAdminPostback_`。`inq|1|…` の形で、管理者の LINE で押されたものだけ） |

**問い合わせ機能の画像の扱い**（INQ_MODE=on）：画像は本文の代わりに「（画像）」として受け付けます（`INQ_messageSummary`）。中身は取り出さず、案件（または対応中の案件への追記）にして、勤怠管理グループへ A-34 を送ります。画像そのものはどこにも保存しません。

### 1-2. 免許の登録・更新中だけ画像を横取りする差し込み位置

`AC_handleEvent_` の「1対1のトークだけを扱う」判定のすぐ後、友だち追加・社員番号・問い合わせの振り分けより前に1行だけ足しました。

```js
if (typeof LIC_onUserEvent_ === 'function' && LIC_onUserEvent_(ev)) return;   // 運転免許証（gas/License.gs・版 2026-11-16b）
```

`LIC_onUserEvent_` が true を返したときだけ、そこで終わります。false なら今までどおりの処理へ進みます。

- LICENSE_MODE が on でなければ、何も読まずにすぐ false を返します（プロパティを1つ読むだけ）。
- true を返すのは次の3つだけです。
  1. postback で、中身が `lic|1|` で始まるもの（免許のボタン）
  2. テキストが「免許更新」「免許登録」だけのもの（前後の空白は無視。ほかの文を含めば対象外）で、その人が在籍・LINE確認済みで、「免許の有無」が「あり」のとき
  3. 画像で、その人が写真の受付中（ボタンか言葉から30分以内。期限を選んだあとは選んでから10分以内・版 2026-11-17a）のとき
- それ以外の画像・テキスト・postback・スタンプ・グループの出来事は、すべて今までと同じ処理になります。言葉が「免許更新」でも、免許なし・未入力・従業員マスタにいない人は、今までどおり問い合わせになります。受付から30分を過ぎた写真も問い合わせになります。
- License.gs が無い場合（`typeof` で確かめる）も、今までどおりに動きます。

### 1-3. DriveApp に新しい権限（OAuth スコープ）が要るか

**新しい権限は要らない見込みです。**

- コード.gs は、すでに `DriveApp.getFolderById`・`getFoldersByName`・`createFolder`・`createFile`・`getBlob` を使っています（TOT の取り込みの「TOT取り込み」フォルダ）。そのため、ドライブ全体の権限（`https://www.googleapis.com/auth/drive`）はもう承認済みです。今回足した `File.setTrashed`・`isTrashed` も同じ権限で動きます。
- LINE の画像の取り出し（`https://api-data.line.me/…/content`）は、今も使っている `UrlFetchApp` の外部通信の権限で動きます。`CacheService` は問い合わせ（Inquiry.gs）・TOT 反映（TotSync.gs）で使っており、権限は要りません。
- 確認の手順（反映のとき）：
  - Apps Script のエディタで License.gs を足して保存し、`licenseSetup` を初めて実行したときに「承認が必要です」が出なければ、権限は変わっていません。
  - もし出た場合（マニフェスト appsscript.json に `oauthScopes` を明示している場合など）は、所有者（会社アカウント）で承認します。権限はプロジェクト単位なので、承認すると既存の時間主導のトリガーもそのまま動きます。Webアプリ（doPost）は「自分として実行」のため、所有者の承認で足ります。どちらも作り直しは要りません。
  - このリポジトリにはマニフェストがないため、明示しているかは本番のエディタの「プロジェクトの設定 →『appsscript.json』マニフェスト ファイルをエディタで表示する」で確かめてください。

**デプロイへの影響**：時間で動く処理（licenseDaily など）は保存した最新のコード（HEAD）で動きますが、doPost はデプロイ済みのバージョンで動きます。受け口の差し込みを有効にするには、**Webアプリの新しいバージョンの公開**が必要です（既存のデプロイを編集して新しいバージョンにする。URL は変わらないので Webhook URL の変更は要りません）。
- 新しいバージョンを公開しないまま LICENSE_MODE=on にすると、毎朝の案内は送られますが、ボタン・「免許更新」・写真を受け付けられません（古い doPost では、問い合わせとして扱われます）。そのため、**on にするのは Webアプリの公開の後**にしてください。

### 1-4. 在籍者・社員番号・LINE ユーザーID の取り方

既存の共通関数を使います。

- 従業員マスタ：`AC_masterSheet_()`（スクリプトプロパティ EMPLOYEE_MASTER_ID）。列は `AC_COL`（A〜N）で、読むだけで書き込みません。
- 社員番号：`AC_cellCode_`（先頭の ' を外す）。
- 在籍：「在籍状況」が「退職」でなく、`AC_isRetired`（退職日の翌日から退職）で退職になっていない人。
- LINE ユーザーID：`AC_isUserId` の形が正しく、「LINE確認済み」にチェックがあり、同じ LINE ID の行がほかにない人だけ使います（ほかの通知と同じ考え方）。それ以外は「LINE 未登録」として扱います。
- 送信：本人あての文は最後に AI の一文を付けます（`AC_withAiNote`。ボタン付きの文はフレックスメッセージのため、License.gs で同じ一文を付けて送ります）。勤怠管理グループは `AC_groupsByDept(...)[AC_ADMIN_GROUP]` で、管理者の個別 LINE は `AC_pushLine_`（LINE_ADMIN_USER_ID）です。どちらにも AI の一文は付けません。
- 送信の記録：`AC_noticeLog_`（「通知送信履歴」。通知ID SAF-01）。エラーは `AC_adminNotice_`（同じ種類は1日1回）。

### 1-5. お知らせ設定の SAF-01 列の扱い（11/16 安藤さんの決定）

- 免許の案内は安全に関わるため、お知らせ設定の「受け取らない」は**適用しません**（License.gs は `AC_noticeCheck_` を呼びません）。今の SAF-01 列のチェック（全員なし）は、免許の案内に影響しません。
- **SAF-01 の列は残します**（列を消すと、「お知らせ設定」シートの列の並びと `AC_NOTICES` の並びがずれるため。版 2026-11-13g のルール17）。
- Notices.gs の `AC_NOTICES` の SAF-01 に、`mandatory: true` と説明（note）「全員必須（安全に関わるため）。この列のチェックでは止まらない」を付けました。
  - 「お知らせ種類」シート（`alcoholCheckSetupNoticeSettings` で毎回書き直す参考の表）の SAF-01 の行は、次のように出ます。
    - 実装状況：「お知らせ設定の対象外（別の仕組みで送る）」
    - 重要度：「全員必須」
    - 止められるか：「止められない（この列のチェックでは止まらない）」
  - ほかの通知の行・「お知らせ設定」シートの列は変わりません。
- **重要な通知（CRIT）には入れません**（11/16 の決定）。

## 2. 「免許証管理」タブ

従業員マスタのファイルに新しく作ります（`licenseSetup`、または LICENSE_MODE が record・on のときの毎朝の処理）。従業員マスタ本体の A〜N 列は変更しません。

| 列 | 入れる人 | 中身 |
|---|---|---|
| 社員番号 | 自動 | 在籍者を毎朝足す（先頭の0を消さないよう ' を付けて入れる） |
| 氏名 | 自動 | 足したときの従業員マスタの氏名（文面の氏名は毎回、従業員マスタから取る） |
| 免許の有無 | **管理本部（手入力）** | 「あり」「なし」、または空欄。「有」「無」「○」「×」も読める |
| 有効期限 | 自動（本人の報告）／管理本部 | 日付。日付として読めない値は「要確認」 |
| 状態 | 自動 | 下の表 |
| 写真ファイルID | 自動 | ドライブのファイルID。最新の回の全部をカンマ区切り（版 2026-11-17a。それより前は1枚） |
| 最終報告日時 | 自動 | 写真・期限を受け取った日時 |
| 送信記録 | 自動 | 実際に送ったもの（on）。1行に1件「種類 期限（または -）送った日」。同じお知らせを2回送らないための記録。**消すと、もう一度送ります** |
| 記録済み | 自動 | 送らずに記録したもの（record・DRY_RUN）。書き方は送信記録と同じ。同じ予定を2回記録しないための記録（on では使わない） |
| 備考 | 自由 | 「その他」で期限を選んだときは、自動で1行足す |

- 列は見出しの名前で探します（並べ替え・列の追加をしても動きます）。見出しが足りないときは右端に足します。
- 退職者の行は消しません（状態を「退職」にして、お知らせの対象から外します）。

| 状態 | 意味 |
|---|---|
| 有無の確認待ち | 「免許の有無」が空欄 |
| 対象外（免許なし） | 「免許の有無」が「なし」（何も送らない） |
| 登録待ち | 「あり」で有効期限がまだない |
| 登録済み | 期限まで31日以上 |
| 更新待ち | 期限まで30日以内（当日を含む） |
| 期限切れ報告なし | 期限を過ぎても新しい期限の報告がない |
| 要確認 | 期限が日付として読めない、または本人が「その他（カレンダー）」で期限を選んだ。**管理本部が状態を消すか直すまで残る**（期限のお知らせは期限の日付どおりに送る） |
| 退職 | 従業員マスタで退職・退職日を過ぎた・マスタにいない（何も送らない） |

## 3. 毎朝の処理（licenseDaily・9時台）

1. 在籍者のうちタブにいない人を足す（免許の有無は空欄）。全員の状態を直す。
2. **免許の有無が空欄の人**：勤怠管理グループへ一覧（A-51）。同じ人は1回だけ。
3. **「あり」で有効期限がない人**（登録）：
   - 1回目：本人へ「運転免許証登録のお願い」（E-80）
   - 3日後・7日後：催促（E-81）。7日後の時点で3日後の催促が未送信なら、1通だけ送る
   - 10日後：まだ登録がなければ、勤怠管理グループへ一覧（A-53）
   - LINE が未登録の人：勤怠管理グループへ一覧（A-52、1回だけ）
4. **期限のお知らせ**（本人へ。段階ごとに1回）：
   - 30日前（期限の8〜30日前の最初の朝）：E-82
   - 7日前（1〜7日前の最初の朝）：E-83
   - 当日：E-84
   - 期限の翌朝以降：本人へ E-85 を送り、勤怠管理グループと管理者の個別 LINE へ一覧（A-54）を送る
   - 同じ人・同じ期限・同じ段階は1回だけです（送信記録の「30日前 2027-03-15 2027-02-13」など）。新しい期限を記録すると、前の期限の段階は送りません（催促が止まります）。
   - 毎朝の処理が動かなかった日があっても、次の朝に今の段階の1通だけを送ります（さかのぼって全部は送りません）。
   - 裏面のお願い（版 2026-11-18b・AI 確認 on）：表面だけ届いて裏面が届かなかった人へ、翌朝以降の最初の朝に1回だけ E-106（送信記録の「裏面の催促 期限 日付」）。
5. 退職者と「なし」の人には何も送りません。お知らせ設定（SAF-01）は適用しません。
6. 送信に失敗した人は、送信記録に残さず次の朝にもう一度送ります。結果は「通知送信履歴」（SAF-01）と「免許証お知らせ記録」に残します。

`licenseRegisterSend`（手動実行）：上の 1〜3 だけを今すぐ行います（初回の一括入力のあとに使う）。期限のお知らせは送りません。

## 4. LINE での登録・更新（LICENSE_MODE=on・Webアプリの新しいバージョンが必要）

1. 本人が「免許証を登録する」「更新を報告する」のボタンを押すか、「免許更新」「免許登録」と送る → E-86 を返信し、**写真の受付を30分**始める（スクリプトのキャッシュに記録）。
2. 受付中に届いた写真 → LINE の画像の取り出し（無料の API）で、すぐに取り出す → LICENSE_FOLDER_ID のフォルダに「社員番号_YYYYMMDD_1」「_2」…の名前で保存（氏名は入れない） → タブの「写真ファイルID」（その回の全ファイルIDをカンマ区切り）「最終報告日時」を更新。
   - **1回の登録・更新（ボタンか言葉で始めた回）の写真はすべて残します**（版 2026-11-17a）。ゴミ箱へ移すのは、次の回の最初の写真を保存したときの、前の回までの写真（同じ社員番号で始まる名前）だけです。
   - 受付の時間：期限を選ぶ前は始めてから30分。期限を選んだあとは、選んでから10分（この間に届いた写真も同じ回の分）。それを過ぎた写真は今までどおり問い合わせになります。期限を早く選んだときは、始めてから30分以内でも、選んでから10分で受付が終わります。
   - 1枚目のあとに期限のボタン（E-87・E-88）を返します。2枚目以降は「n枚目の写真も保存しました。ありがとうございます。」（E-96）だけを返し、ボタンは重ねて出しません。
   - 表・裏を続けて送ると LINE の出来事がほぼ同時に届くため、保存から記録までを1つのロックの中で行います（同じ番号になったり、互いをゴミ箱へ移したりしないため）。
   - 写真は問い合わせには入りません（問い合わせのシート・勤怠管理グループへのお知らせは無し）。
   - 取り出し・保存に失敗したら、本人へ E-94、管理者へ A-57（1日1回）。受付は続くので、30分以内なら送り直せます。
3. 期限を選んでもらう（返信。6時間まで有効）：
   - **登録**（今の期限がない）：カレンダー（datetimepicker・mode=date）だけ（E-87）
   - **更新**（今の期限がある）：「今の期限の3年後の日付」「5年後の日付」「その他（カレンダーで選ぶ）」（E-88）
4. 選ばれた期限を記録してお礼（E-89・E-90）。状態を直す。
   - 「その他」：記録したうえで状態を「要確認」にし、備考に1行足し、管理者の個別 LINE へ A-55。
   - 今日以前の日付：記録せず、もう一度選んでもらう（E-92）。
   - 同じボタンを2回押した・別のボタンを続けて押した：上書きせず E-91。
   - 時間切れ・古いボタン：E-93（もう一度「免許更新」から）。
5. LINE の再送（同じ webhookEventId）は1回だけ処理します。

### 4-2. AI による写真の確認（LICENSE_AI_CHECK・版 2026-11-18a）

写真ごとに、写真だけを Claude API（既定 claude-sonnet-5-5・JSON で返させる）へ送り、「免許証か／表か裏か／読めるか／問題の種類（ぼやけ・暗い・反射・はみ出し・免許証以外）／有効期限（読めたら YYYY-MM-DD）」を受け取ります。氏名・社員番号・LINE ID は送りません。

| LICENSE_AI_CHECK | 本人への流れ | タブ |
|---|---|---|
| 未設定・off（**最初はこれ**） | 今までどおり（写真のあと期限のボタン） | 変えない |
| record | off と同じ（再送のお願いもしない） | 「AI確認」に判定を記録（例「記録：OK（表面・期限 2029-04-30）」「記録：再送依頼相当（暗い）」）。ボタンで選んだ期限が写真と違えば「記録：要確認（日付違い・写真 …）」。状態は変えず、安藤さんへも送らない |
| on | 下のとおり | 「AI確認」と状態を更新 |

**on の流れ**
1. 読めない写真（ぼやけ・暗い・反射・はみ出し・免許証以外・表面なのに期限が読めない）：**保存しない**。理由と撮り方のコツを添えて、**その面**（表面を記録したあとなら裏面、裏面だけ届いているなら表面）の再送をお願いし（E-97）、受付を延ばす。「AI確認」は「再送依頼（理由）」。
2. 表面から期限が読めた：期限は**この時点で記録**する（「AI確認」は「OK」）。お礼はまだ送らず、「表面の写真を確認しました。続けて、裏面の写真をお送りください。」（E-103）だけを返す。裏面はそこから30分受け付ける。
3. 裏面が届いた（表面のあと）：保存して、お礼と記録した日付を1回だけ送る（E-98・E-99。登録か更新かは、受付を始めたときの期限で決める）。
4. 裏面が先に届いた：保存して「裏面の写真を受け取りました。続けて、表面の写真をお送りください。」（E-100）。表面が届いたら期限を記録してお礼（E-98・E-99）。
5. 表と裏を続けて送ったときも、上の順で写真1枚に1通まで。LINE で2枚を一緒に選んで送ったとき（LINE の imageSet）は、最後の1枚の処理のときだけ返す（返すのは、お礼か、読めなかった面の再送のお願いの1通）。写真はロックの中で1枚ずつ扱うので、同時に届いても文は重ならない。
6. お礼のあとの写真（10分以内）：保存だけで返信しない（E-96「n枚目の写真も保存しました」は、on では使わない）。別の写真から違う期限を読み取ったら要確認・安藤さんへ。
7. 表面だけで、裏面が30分以内に届かない：期限は記録したまま。送信記録の列に「裏面待ち 期限 日付」を付け、**翌朝の毎朝の処理で1回だけ**本人へ「裏面の写真がまだ届いていません。…『免許更新』と送り、裏面の写真をお送りください。」（E-106・ボタンなし）。その回は表面を受け付けたことにする。そのあと14日以内に「免許更新」と送った人は、裏面だけの受付（E-104）になり、裏面でお礼（E-105）。前の写真は消さない。
8. 読み取った日付の確かめ：今日より1年以上前・今日から10年以上先・更新で**前の期限より前** → 記録したうえで状態を「要確認」、「AI確認」を「要確認（日付の範囲外）」「要確認（前の期限より前）」にし、安藤さんの個別 LINE へ社員番号と日付だけ（A-59）。**前と同じ日付は正しい再登録として扱い、要確認にしない**（版 2026-11-18b で直した。18a では「前の期限以前」で要確認になっていた）。
9. 同じ回で2回続けて読み取れない：表面より前なら、今の期限のボタン（3年後・5年後・カレンダー。E-101・E-102）を出し、状態を「要確認」、安藤さんへ社員番号だけ（A-59）。ボタンで選んでも要確認のまま。表面を記録したあと（裏面が2回続けて読めない）は、写真を保存してお礼で終える（免許証以外の写真は保存せず、翌朝に裏面をお願いする）。
10. AI が使えない（キー未設定・1日の上限・エラー・時間切れ・断られた・応答が読めない・写真が大きすぎる）：表面より前なら、保存して今までと同じ期限のボタン（E-87・E-88）を出し、状態を「要確認」、「AI確認」を「未確認（理由）」、安藤さんへ社員番号だけ（A-59）。表面を記録したあとなら、裏面として保存してお礼。キー未設定・上限・エラーは、理由ごとにその日1回だけ管理者へ（A-58）。
11. ボタンで選んだ期限が、同じ回の写真から読み取った期限と違う：状態を「要確認」、安藤さんへ社員番号と2つの日付（A-59）。

- 1日に AI へ送る枚数は、ユーザープロパティ（送信記録と同じ場所）の `stat:日付:lic-ai` で数えます（40日で自動で消える）。
- 手動実行 `licenseAiRecheck`：「写真ファイルID」の写真をまとめて AI で確認し、読み取った期限とタブの期限を比べて「AI確認」に書きます（「OK（再確認 日付）」「要確認（日付違い・写真 …・再確認 日付）」「未確認（…）」）。**本人へは何も送らず、状態も変えません**。LICENSE_AI_CHECK に関係なく動きます（キーは必要）。ログは社員番号と結果の種類だけ。5分・1日の上限で止まります。
- 断られた（refusal）ときのモデルの切り替え（fallbacks）は付けていません。Sonnet 5.5 の切り替えは免許証の写真で起こりうる種類の断りを対象にしないためで、断られたら上の 7 の扱いにします。

## 5. 動作モード（スクリプトプロパティ LICENSE_MODE）

| 値 | 毎朝の処理 | LINE の受け口 |
|---|---|---|
| 未設定・off（**最初はこれ**） | 何もしない | 今までどおり（「免許更新」も写真も問い合わせ） |
| record | タブの行の追加・状態の更新をして、送る予定の文を「免許証お知らせ記録」に書く。**LINE は送らない**。同じ人・同じ期限・同じ段階は**1回だけ記録**する（「記録済み」の列で管理。催促の3日後・7日後も記録した日から数える）。「送信記録」は付けないので、on にすると今の段階を改めて送る | 今までどおり |
| on | 送る（DRY_RUN が false のときだけ。それ以外は record と同じ） | 免許の言葉・ボタン・受付中の写真を扱う |

### 5-2. 送る範囲（スクリプトプロパティ LICENSE_SCOPE・版 2026-11-16c）

まず管理本部の全員だけで本番テストするための設定です。

| 値 | 本人あて（登録のお願い・催促・30日前・7日前・当日・期限切れ） | 勤怠管理グループ・管理者への一覧（有無の確認・LINE 未登録・登録なし・期限切れ） |
|---|---|---|
| 未設定・空（今までどおり） | 全員 | 全員の分 |
| 所属名（例 `管理本部`） | 従業員マスタの所属がその名前の人だけに送る。**範囲外の人は「記録のみ」**（「免許証お知らせ記録」に結果「記録のみ（範囲外・送信なし）」で書くだけ） | 範囲内の人の分だけ（範囲外の人は一覧に入れない） |

- 所属の判定は、従業員マスタの所属の列（E列。お知らせ設定・部門のグループと同じ列）の値を、前後の空白を除いて**完全に一致**するかで見ます。新しい列は作りません。
- 範囲外の人は、**「送信記録」にも「記録済み」にも印を付けません**。そのため、LICENSE_SCOPE を空にする（範囲を外す）と、次の朝（または licenseRegisterSend）で、範囲外だった人に今の段階の案内が送られます。
- そのかわり、範囲外の人の「記録のみ」の行は**毎朝**「免許証お知らせ記録」に増えます（送信はしません。1朝あたり範囲外で案内の対象になる人数ぶん）。
- 範囲内の人は今までどおり、同じ人・同じ期限・同じ段階は1回だけです。
- LINE の受け口（「免許更新」・写真・ボタン）は範囲で制限しません（お願いが届いた人だけが使う前提）。
- record のときも同じです（範囲内は「記録済み」に付け、範囲外は付けない）。
- 確認用の手動実行 `licenseScopePreview`（送信なし・シートも変えない）：範囲の値、範囲内の在籍者の人数と社員番号、うち LINE 未登録の人数と社員番号、「今 licenseRegisterSend を実行したら登録のお願いが届く人」の人数と社員番号、範囲外の人数をログに出します。氏名・LINE ID は出しません。所属名が従業員マスタの在籍者に無いとき（綴りの違いなど）は注意を出し、範囲内は0人になります。

AI の確認の設定（版 2026-11-18a。どれも安藤さんが設定する。未設定でも動く）：ANTHROPIC_API_KEY（API キー。コード・ログ・GitHub に書かない）、LICENSE_AI_CHECK（off／record／on。未設定は off）、LICENSE_AI_MODEL（未設定なら claude-sonnet-5-5）、LICENSE_AI_DAILY_MAX（未設定なら 200）。

ほかに使うスクリプトプロパティ：LICENSE_FOLDER_ID（写真のフォルダ。新しく作る）、LINE_CHANNEL_ACCESS_TOKEN・LINE_ADMIN_USER_ID・EMPLOYEE_MASTER_ID・DRY_RUN（今のもの）。
