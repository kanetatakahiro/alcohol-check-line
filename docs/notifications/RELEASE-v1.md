## 手順

### 1. コードの反映（安藤さん・Apps Script の画面）

1. Apps Script「勤怠・アルコールチェック管理」を開きます。
2. 「コード.gs」の中身をすべて消し、GitHub の feature/notification-settings の gas/AlcoholCheck.gs を貼り付けて保存します。
3. 「LeaveRequest.gs」も同じように gas/LeaveRequest.gs に置き換えて保存します。
4. 「ファイル」の「＋」→「スクリプト」で、名前を `Notices` にしたファイルを作り、gas/Notices.gs を貼り付けて保存します。
5. 関数 `alcoholCheckShowSettings` を実行し、1行目が「コードの版：2026-11-09c」、設定の一覧に `NOTICE_SETTINGS`・`ALERT_TO_GROUP` などが出ることを確かめます。
6. 3つのファイルの中身を Claude に渡していただければ、指紋を照合します。

**この時点で変わること**：飲酒検知・異常値の通知（CRIT-01）が、管理者の個別LINEに加えて勤怠管理グループにも届きます。送信先ごとの結果は「通知送信履歴」シートに残ります（シートは最初の通知のときに自動で作られます）。

- グループへの送信をまだ始めたくない場合は、**保存の前に**スクリプトプロパティ `ALERT_TO_GROUP` ＝ `false` を足してください（管理者だけの今の動きのまま）。

**変わらないこと**：アルコールチェックの案内・催促・お礼、勤怠の通知、希望休の案内、問い合わせ管理、受け口（Webアプリのバージョン21のまま）、既存のトリガー8件。

### 2. 夜の取り込みの見守りのトリガー（安藤さん）

1. 関数 `alcoholCheckSetupNightWatchTrigger` を実行します。
2. 「トリガー」画面に `alcoholCheckNightRelayWatch`（分ベースのタイマー・15分おき）が1つあることを確かめます。既存の8件はそのままです。
3. その日の 22:45 以降、取り込みが届いていれば「通知送信履歴」に「取り込みを確認（通知なし）」の行が1つ書かれます。届いていなければ勤怠管理グループへ1通届きます。

### 3. 「お知らせ設定」のシート一式を作る（安藤さん）

1. 関数 `alcoholCheckSetupNoticeSettings` を実行します。従業員マスタのファイルに次のシートができます：お知らせ設定・所属別お知らせ設定・お知らせ種類・お知らせ設定履歴・通知送信履歴。
2. 既存のシート（従業員マスタ・お知らせ停止・LINE文面・LINEグループなど）と、従業員マスタの A〜O 列は変わりません。
3. 何度実行しても重複しません（新しい人・新しい所属だけが足されます。管理本部が直したチェックは上書きしません）。
4. 関数 `alcoholCheckNoticeSettingsPreview` で、通知ごとの ON の人数（氏名なし）を実行ログで確かめられます。

### 4. 初期値の確認（管理本部）

- 「所属別お知らせ設定」：決定済みの4項目（希望休・打刻漏れ・申請の確認・残業の警告）のほかは、今の動きを引き継ぐ値になっています（DESIGN-v1.md 1章）。直したい所属があればチェックを変えてください。
- 「お知らせ設定」：希望休の除外の11件が ATT-01 の OFF になっていること、リスタイルの人が ATT-01 OFF になっていることを確かめます。

### 5. 記録だけで始める：`NOTICE_SETTINGS=record`

- スクリプトプロパティ `NOTICE_SETTINGS` ＝ `record` を足します。
- 送信は今までどおりで、チェックが OFF の人に通知が出るはずだった時だけ「通知送信履歴」に「お知らせ設定でOFF（記録のみ・送信は今までどおり）」が書かれます（1人・1通知・1日1行）。
- 数日（10日の希望休の案内を含めると安心です）記録を見て、意図どおりかを Claude が確認します。

### 6. 設定に従う：`NOTICE_SETTINGS=on`

- `NOTICE_SETTINGS` を `on` に変えます。チェックが OFF の人には、その通知を送りません（「通知送信履歴」に「お知らせ設定でOFFのため送らない」）。
- ATT-03・ATT-04 が止めるのは、推奨の設定（`NOTICE_ALCOHOL_SCOPE` 未設定）では 8:30・18:30 の案内だけです。10:00・20:00 の未入力の催促、お礼、飲酒検知は止まりません。
- 1か月ほど使ったら、`LEAVE_REQUEST_EXCLUDE_CODES` を消して「お知らせ設定」だけで管理できます（消す前に、11件が OFF になっていることを確認）。

### 7. （後日）Webアプリの新しい版の公開

- 受け口（doPost）で動く本人への勤怠の通知（ATT-02 打刻漏れ・HR-02 残業の警告・HR-04 最大残業時間の超過）に設定を効かせるには、Webアプリの新しい版の公開が必要です。
- 管理者の毎朝の「承認待ちの申請」の一覧（AC_adminAttendanceChecks_）も受け口で動くため、「新しく増えた申請だけ」になるのは版の公開の後です。それまでは今までどおり、承認待ちの全件を毎朝1通お知らせします（今の設定で送られている場合）。
  - 公開した最初の朝は、その時点の承認待ちの全件が「新しい申請」として1回だけ届きます。翌日からは増えた分だけになります。今は `ATTENDANCE_NOTIFY` が未設定でこれらは本人へ送っていないため、急ぎません。勤怠の本人向けを始めるときに一緒に行います。

### 8. 本人への承認待ちのお知らせ：`REQUEST_SELF_NOTIFY`（管理本部の本人だけ）

1つの申請につき1回だけ知らせます（2026-11-09 安藤・社長 承認）。承認は月末にまとめて行うため、一度知らせた申請は、承認・取消されるまで2度目は知らせません。新しい申請が無い日は送りません。この処理は1時間ごとのトリガーで動くので、Webアプリの版の公開は要りません（手順1の後から使えます）。

1. スクリプトプロパティ `REQUEST_SELF_NOTIFY` ＝ `record` を足します（送らずに「承認待ち本人通知」シートへ記録するだけ）。
2. 翌朝 7〜12時の間に、「承認待ち本人通知」シートに「記録のみ（送信しない）」の行ができることを確かめます。次の朝は、新しい申請のある人の行だけが増えます（同じ申請の行は増えません）。
3. 数日見て問題が無ければ、`REQUEST_SELF_NOTIFY` を `on` に変えます（`DRY_RUN` が `false` のときだけ送ります）。
   - `on` にした最初の朝は、まだ本人へ届いていない承認待ちの申請を1回だけ1通で送ります（`record` の間の記録は「知らせた」に数えません）。
   - 翌日からは、新しい申請のある人にだけ、その新しい申請だけを1通で送ります。
4. 「承認待ち本人通知」シートで「送信」の行を確かめます。送信に失敗した申請は記録されず、翌朝にもう一度送ります。
5. 止めるときは `REQUEST_SELF_NOTIFY` を削除します。お知らせ停止中の人・お知らせ設定（HR-01）が OFF の人には送りません（`NOTICE_SETTINGS=on` のとき）。

記録：`reqseen:self:…`（送った）、`reqseen:selfrec:…`（記録だけ）、`reqseen:admin:…`（管理者の一覧）。8日で消える `sent:` とは別の名前で、申請が承認待ちの一覧から消えた朝に自動で消えます。TOTの申請データが一部読めなかった朝は、消さずに残します。

### 9. 夜22:30の本人向けの勤怠のお知らせ（1人1晩1通・版 2026-11-09d）

11/9 15:30 に版 2026-11-09c（`d1a5765db4ccd366`）が反映済み。そこからコード.gs だけを差し替えます（LeaveRequest.gs・Notices.gs・Inquiry.gs はそのまま）。11/13（金）の夜から本人へ送る予定（安藤・社長 承認済み）。

**今の動き（調査結果）**：夜の処理は VPS からの doPost（Webアプリ公開版 v21）。本人へは `ATTENDANCE_NOTIFY` 未設定のため送っていません。`ATTENDANCE_TEST=true`（DRY_RUN=false）なので、本人へ送る予定の文面が管理者へ1晩1通のまとめ（【勤怠テスト】、同じ内容は1回）で届き、残業45時間の管理者通知も届いています。

1. 「コード.gs」を feature/notification-settings の gas/AlcoholCheck.gs（`038908a8112f1372`）に差し替えて保存します。`alcoholCheckShowSettings` で「コードの版：2026-11-09d」を確かめます。
2. `alcoholCheckNightSelfPreview` を実行します（送らない・記録しない）。22:30 より前は朝のデータなので、当日の打刻の項目は入りません。人数・項目・文面の例を確かめます。
3. スクリプトプロパティ `ATTENDANCE_NOTIFY` ＝ `record` を足します。
4. Webアプリの**既存のデプロイを編集**して新しいバージョンを公開します（「デプロイを管理」→ 鉛筆 → バージョン「新バージョン」→ デプロイ。新しいデプロイは作らない・URL は変わらない）。夜の処理はこの公開版で動くため、これが無いと手順3は効きません。
5. その夜 22:30 の後、「通知送信履歴」に「記録（送信しない）」の行と文面（9列目）ができることを確かめます。`ATTENDANCE_TEST=true` のままなら、管理者へまとめた文面の【勤怠テスト】が届きます。
6. 翌日（11/13）、記録に問題が無ければ `ATTENDANCE_NOTIFY` を `on` に変えます（版の公開は不要）。その夜から本人へ1人1通。`NOTICE_SETTINGS` は `on` のままで構いません（夜のまとめは NOTICE_SETTINGS の値にかかわらずチェックに従います）。
   - `on` にした最初の晩は、まだ本人へ届いていない内容（過去7日の打刻漏れ・今月の残業30h／45h）を1回だけまとめて送ります（record の間の記録は「送った」に数えません）。
   - `ATTENDANCE_TEST` は `on` の間は動かないので、`on` にした後に削除してください（残しても送られません）。

**戻し方**：`ATTENDANCE_NOTIFY` を削除（本人へ送らない今の動きに戻る・版の公開は不要）。コードごと戻すときは「コード.gs」を `d1a5765db4ccd366`（版 2026-11-09c）に戻し、既存のデプロイを編集して新しいバージョンを公開します（`ATTENDANCE_NOTIFY` を先に削除しておくこと。2026-11-09c は `true` 以外を「送らない」として扱います）。
