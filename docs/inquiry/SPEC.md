# 従業員問い合わせ管理 第1段階 仕様書（案）

状態：**実装済み・本番未導入**（2026-11-05、ブランチ feature/inquiry、版 2026-11-05a）。調査結果は [INVESTIGATION.md](INVESTIGATION.md)、本番への反映は [RELEASE.md](RELEASE.md) を参照してください。
「（要決定）」だった項目は、調査でのおすすめのとおりに実装しました（下の「12. 実装で決めたこと」）。変える場合は承認時にお知らせください。

## 1. 目的
従業員が公式LINEに1対1で送った問い合わせを、**取りこぼさず・二重に対応せず**に管理本部で受け付けます。
- 届いた問い合わせは、勤怠管理グループにすぐ知らせます。
- 対応の状況（未対応・対応中・対応済み）を記録します。
- 残っている案件を1日2回知らせます。
- 返信は今までどおり、スタッフがLINE公式アカウントのチャット画面から行います。システムは返信の内容を読みません（読めません）。

## 2. 構成
```
従業員（1対1のトーク）
  → LINE → （今：Apps Script に直接／Workers に切り替えた後：Workers → Apps Script）
     → 既存の doPost → AC_handleEvent_ → 社員番号でなければ INQ_onUserEvent_（新しいファイル gas/Inquiry.gs）
         → 問い合わせ専用のスプレッドシートに記録 → 勤怠管理グループへ通知（ボタンつき）
勤怠管理グループのボタン（postback）
  → AC_handleGroupEvent_ → INQ_onGroupPostback_ → 状態を更新 → 返信（送信数に数えない）
9:00・17:00 の時刻指定トリガー → INQ_remind → 未対応・対応中があれば勤怠管理グループへ1通
```
- 既存の「コード.gs」への変更は3行（受信処理から `INQ_` の関数を呼ぶだけ）です。詳しくは INVESTIGATION.md の「4. 追加する場所」を参照してください。
- 関数・定数・設定・シートの名前は `INQ_`／「問い合わせ」で始めます。既存（`AC_`）・社員管理AI（`EA_`）とぶつからないようにするためです。
- 土台の版は本番の版（2026-10-27b）です。main への統合は PR #2 で確認中です。

## 3. 受付の判定（1対1のトーク）
届いたメッセージを、上から順に判定します。

| 順 | 条件 | 扱い |
|---|---|---|
| 1 | `INQ_MODE` が未設定・`off` | 何もしない（今と同じ） |
| 2 | 同じイベントをすでに処理した（webhookEventId・メッセージの番号） | 何もしない |
| 3 | 送信者のプロフィールが取れない（友だちでない・偽のデータ） | 案件にしない。「受信記録」に「実在確認できず」と残す |
| 4 | 社員番号だけのメッセージ（4〜6桁） | 既存の登録の処理（問い合わせにはしない） |
| 5 | 定型連絡（下の 3-1） | 案件にしない。「定型連絡」タブに記録だけ残す |
| 6 | 同じ人の未完了（未対応・対応中）の案件がある | その案件に**追記**する（下の 3-3） |
| 7 | それ以外 | **新しい案件**として受け付ける |

- 文字以外のメッセージも扱います。
  - 画像・動画・音声・ファイル・位置情報：内容を「（画像）」などと記録して、案件として扱う。画像そのもの・ファイル名は保存しない。
  - スタンプ：定型連絡と同じく記録だけ（「（スタンプ）」）。
- 友だち追加・ブロック（follow / unfollow）は、問い合わせの処理では扱いません（友だち追加は既存のあいさつのまま）。

### 3-1. 定型連絡（案件にしない）
- メッセージ全体が、次のどれかにだけ当たるときに定型連絡とします。前後の空白・句読点・「！」「。」・絵文字・「です」「します」「しました」「ます」は無視します。
  - 出勤／退勤／遅刻／早退／休憩／休憩入り／休憩終わり／休憩終了／戻りました／お疲れさまです（「お疲れ様です」「お疲れさまでした」も同じ）
  - 全体が15文字を超えるものは、定型連絡にしません
  - 例：「退勤」「退勤しました。」「遅刻します🙏」→ 定型連絡
- **長い文や相談を含む文は案件にします**（取りこぼさない側に倒す）。
  - 例：「遅刻します、電車が止まっていて30分遅れます」→ 案件
  - 例：「遅刻の扱いについて教えてください」→ 案件
- 定型連絡は、日時・社員番号（分かる場合）・内容を記録するだけです。グループには知らせません。
- 言葉の一覧はスクリプトのプロパティ `INQ_ROUTINE_WORDS` で足せるようにします（既定は上の一覧）。

### 3-2. 送信者と従業員の紐付け
| 従業員マスタの状態 | 表示 | 登録の案内 |
|---|---|---|
| LINEユーザーIDが一致し、「LINE確認済み」にチェックあり（1行だけ） | 氏名・所属 | なし |
| IDは一致するが、チェックなし | 確認待ち（LINE表示名） | なし（登録は済んでいるため） |
| IDが一致する行が無い | 未登録（LINE表示名） | **1回だけ**返信で案内（下の文） |
| IDが一致する行が2つ以上 | 要確認（LINE表示名）。従業員マスタの重複を直す必要がある | なし |

- 氏名・LINE表示名から推測して紐付けることはしません。
- 退職者（在籍状況が「退職」、または退職日を過ぎた人）は、氏名に「（退職）」を付けて表示します（例：○○ ○○（退職）（所属））。受付はします。
- 未登録の人への案内（返信。送信数に数えない。同じLINEユーザーには1回だけ。記録は「案内済み」タブ）：
  > お問い合わせありがとうございます。担当者から順にご連絡いたします。
  > 社員の方は、お手数ですが社員番号（数字のみ）をこのトークに送ってください。LINEの登録が完了します。
  （文面は確定前の案。従業員向けの文面はChatGPTで確定したものに差し替える）

### 3-3. 追記
- 同じ人に未完了の案件があれば、新しい案件は作らず、その案件の「やりとり」タブに追記します。追記の回数と最終受信日時も更新します。
- 案件の状態ごとの扱い：
  - **未対応の案件**への追記：グループには知らせない（リマインドに含まれる）
  - **対応中の案件**への追記：グループへ短く知らせる。**同じ案件では30分に1回まで**
    - 例：`【問い合わせ・追記】Q-20261105-003 ○○さん（所属）から追記があります。チャットをご確認ください`
    - 30分以内の2回目以降は記録だけ
  - 対応済みの案件は対象外（新しい案件になる）

## 4. 勤怠管理グループへの通知
- 送り先は「LINEグループ」シートで部門が「勤怠管理」（`AC_ADMIN_GROUP`）の有効なグループです。
- 登録が無い・送信に失敗したときは、管理者の個別LINE（既存の `AC_pushLine_`）へ送ります。

### 4-1. 新しい問い合わせ
```
【問い合わせ】Q-20261105-003
従業員：○○ ○○（法人カーケア）
受付：11/5（木） 14:12
内容：「明日のシフトの件で確認したいことが…」
状況：未対応
［対応します］［対応済みにする］
```
- 内容は**冒頭20文字**です（改行は空白に置き換え、20文字を超えたら「…」）。全文はLINEのチャット画面で見ます。
- **機密を含むとき**は、内容を「（内容はチャットで確認）」と表示します（下の 4-3）。
- ボタンは postback です。中身：`inq|1|take|Q-20261105-003|<合言葉>`、`inq|1|done|…`
  - 合言葉：案件ごとの推測できない6文字。シートにだけ保存する。
  - 押したときに出る文字（displayText）：「対応します（Q-20261105-003）」「対応済みにします（Q-20261105-003）」
- メッセージの形：Flex Message（本文の下にボタン2つ）。通知を受け取る人が「新しいメッセージ」の一覧で見る文（代替テキスト）は「【問い合わせ】案件番号 従業員」です。
- 勤怠管理グループが未登録・送信に失敗したときは、管理者の個別LINEへ文字だけで送ります。

### 4-2. ボタンを押したとき
- INVESTIGATION.md「5-3」の表のとおりです。
  - 状態は「未対応 → 対応中 → 対応済み」の一方向だけ。押したときにシートの今の状態を読み直す。
  - 合言葉が合わないとき・勤怠管理グループ以外で押されたとき・押した人がメンバーでないときは、何も変えない。
- 結果は返信で知らせます（送信数に数えない）。
  - 例：`Q-20261105-003 を ○○さんが対応中にしました`
  - 例：`Q-20261105-003 は対応済みです（11/5 15:02・○○さん）`
- 押した人のLINE表示名とユーザーIDを、担当者・完了者として記録します。

### 4-3. 機密の判定
次のどれかを含むときは、通知・リマインドに内容を出しません。
- 言葉：パスワード、パスコード、暗証番号、口座、口座番号、カード番号、クレジット、セキュリティコード、マイナンバー、個人番号、PIN、password（大文字・小文字・全角を区別しない）
- 数字：7桁以上の数字の並び
  - 全角数字は半角にそろえて判定する
  - 数字の間の空白・「-」・「ー」は詰めて数える（例：`1234-5678-9012-3456`、`090-1234-5678` も該当。電話番号も伏せる側に倒す）
- 言葉の一覧は `INQ_SECRET_WORDS` で足せるようにします。
- シートへの保存：機密の部分を「＊＊＊」に伏せて保存し、「機密あり」にチェックを付けます。
  - 7桁以上の数字（区切りを含む）は「＊＊＊」
  - 機密の言葉がある行は、その言葉より後ろを「＊＊＊」にする（例：「口座番号は1234567です」→「口座＊＊＊」）
  - 全文はLINEのチャット画面で見ます

## 5. リマインド（9:00・17:00）
- 未対応・対応中の案件があるときだけ、勤怠管理グループへ**1通にまとめて**送ります。0件なら送りません。
- 時刻指定のトリガーは前後15分程度ずれます（既存と同じ）。
- 既定は毎日送ります。`INQ_REMIND_DAYS=weekdays` にすると土日は送りません（祝日は判定しません）。
```
【問い合わせ・未完了 3件】11/6（金） 09:00
・Q-20261105-003 ○○さん（法人カーケア）未対応【前日から継続】
  「明日のシフトの件で確認したいことが…」
・Q-20261106-001 未登録（LINE表示名）未対応
  「（内容はチャットで確認）」
・Q-20261105-001 ○○さん（管理本部）対応中：△△さん【前日から継続】
  「有給の残りを教えてください」
```
- 並び順：未対応 → 対応中、それぞれ受付の古い順。
- 受付日が前日以前の案件には「前日から継続」と付けます。
- 1通は4,900文字までです。超えるときは件数だけを書いて「ほか○件」とします。

## 6. 記録（問い合わせ専用の新しいスプレッドシート）
ファイル名「従業員問い合わせ管理」。管理本部だけで共有します（従業員マスタとは別のファイル）。ファイルのIDはスクリプトのプロパティ `INQ_SPREADSHEET_ID` に置きます。

| タブ | 1行の内容 |
|---|---|
| 問い合わせ | 案件番号・状態・社員番号・氏名・所属・紐付け（登録済み／確認待ち／未登録／要確認）・LINEユーザーID・LINE表示名・受付日時・内容（冒頭）・機密あり・最終受信日時・追記の回数・担当者・担当者ID・対応開始日時・完了者・完了者ID・完了日時・最後の追記通知・合言葉・作成時のイベント番号 |
| やりとり | 日時・案件番号・種類（受付／追記／対応開始／対応済み／ボタン拒否）・内容・LINEユーザーID・イベント番号・メッセージ番号 |
| 定型連絡 | 日時・社員番号・氏名・LINEユーザーID・内容・イベント番号 |
| 受信記録 | 日時・イベント番号・結果（受付・追記・定型連絡・実在確認できず・ボタンの結果など）。内容は書かない。重複の確認に直近2,000行を使う |
| 案内済み | LINEユーザーID・案内日時 |

- 案件番号：`Q-YYYYMMDD-NNN`（受付日ごとの連番）
- 書き込みは既存と同じスクリプトの鍵の中で行います（同時の受信でも番号や案件が重ならない）。
- 行の削除・並べ替えは、管理本部が手で行わない前提です（必要なら別のタブに絞り込みの表を作る）。
- 保存期間：第1段階では消しません（必要になったら決める）。

## 7. 重複受信・安全対策
- 重複：webhookEventId（一時記憶6時間）＋シートのイベント番号・メッセージ番号で二重に確かめます。Workers の24時間の再送にも対応します。
- 実在確認：1対1は送信者のプロフィール、ボタンはグループのメンバーを確かめます。
- 偽のボタン：案件ごとの合言葉で防ぎます。Workers の転送の印（`?ts=…&sig=…`）での確認は第2段階で検討します（Workers の変更が必要なため）。
- エラーで既存の処理を止めません。`INQ_` の入口の関数は、すべてのエラーを中で受け止めます。続けて失敗するときは、管理者へ1日1回まで知らせます（既存の `AC_adminNotice_` を使う）。
- 実行ログ・通知に書かないもの：トークン・合言葉。実行ログには問い合わせの本文も書きません。
- 「Inquiry.gs」が無いときでも、「コード.gs」は呼び出しの前に関数があるかを確かめるため、エラーになりません。

## 8. 将来のAI自動返信との関係（第1段階では作らない）
- `INQ_activeCaseFor(userId)` を用意し、未対応・対応中の案件があるかを返せるようにします。
- 将来のAI自動返信は、**対応中の案件がある人には返信しない**決まりにします（スタッフの返信とぶつからないため）。

## 9. 設定（スクリプトのプロパティ・本番承認後に登録）
| 名前 | 値 | 意味 |
|---|---|---|
| `INQ_MODE` | 未設定・`off` / `record` / `on` | 何もしない／記録だけ（グループに送らない・案内も送らない）／利用開始 |
| `INQ_SPREADSHEET_ID` | ファイルのID | 記録先 |
| `INQ_NOTIFY_TO` | 未設定・`admin` | `admin` のときは勤怠管理グループではなく管理者の個別LINEへ送る（試験用。管理者の個別LINEのボタンも使える） |
| `INQ_REMIND_DAYS` | 未設定・`all` / `weekdays` | リマインドを毎日／平日だけ |
| `INQ_ROUTINE_WORDS`・`INQ_SECRET_WORDS` | 「、」区切り | 定型連絡・機密の言葉の追加（任意） |

- 用意する関数：`INQ_setup`（シートと見出しを作る）、`INQ_setupTriggers` / `INQ_removeTriggers`（9:00・17:00）、`INQ_stop`（`INQ_MODE` を off にする）、`INQ_preview`（今の未完了の一覧を実行ログに表示。送信なし）

## 10. 本番導入の流れ（それぞれ承認を得てから。詳しくは RELEASE.md）
1. 土台の版の整理（本番の版 2026-10-27b を main に統合）
2. 問い合わせを含まない今の版で、Webアプリの新しい版を発行する
   - 「デプロイを管理」で既存のデプロイを編集する（URLを変えない）
   - 事前に tmpSetup.gs の中身と、コード.gs の指紋を確認する
   - 月末の前後は避ける
   - 数日、登録・部門登録・ToTの取り込みを確認する
3. 問い合わせ専用のスプレッドシートを作る → 「コード.gs」の3行と `Inquiry.gs` を反映する → `INQ_setup` → 新しい版を発行する（`INQ_MODE` は未設定のまま。動きは今と同じ）
4. `INQ_MODE=record` で数日、記録だけを確認する
5. `INQ_MODE=on`・`INQ_NOTIFY_TO=admin` で管理者だけの試験をする（ボタン・二重押し・古いボタン・追記の通知）
6. `INQ_NOTIFY_TO` を消して勤怠管理グループへ → `INQ_setupTriggers`

- 戻し方：`INQ_MODE=off`（すぐに止まる）。コードごと戻すときは、「デプロイを管理」で前の版を選び直す。

## 11. 第1段階に含めないもの
- 返信の内容の記録（システムからは読めない）
- AIによる自動返信・分類
- 従業員への自動の「受け付けました」返信（LINEの応答メッセージと二重になるおそれがあるため）
- Workers の転送の印の確認
- 画像・ファイルの保存
- 対応済みの案件の取り消し（必要なら管理本部がシートで直す。第2段階で検討）

## 12. 実装で決めたこと（調査でのおすすめのとおり）
| 項目 | 決めたこと |
|---|---|
| 「受け付けました」の自動返信 | 送らない（未登録の人への社員番号の案内だけ、1回） |
| 機密を含むメッセージの保存 | 機密の部分を「＊＊＊」に伏せて保存 |
| リマインドの曜日 | 毎日（`INQ_REMIND_DAYS=weekdays` で土日は止められる。祝日は判定しない） |
| スタンプ | 記録だけ（案件にしない） |
| 勤怠管理グループの人数 | 不明（送信数の見込みは月 約70〜100 × 人数） |
