# 公式LINEのAI化：調査結果（第1弾の実装方法と、第2弾・第3弾の前提）

状態：調査のみ（2026-11-06）。**コード・本番（Apps Script・デプロイ・トリガー・スクリプトプロパティ・LINE・Webhook・従業員マスタ）は変更していません。Claude API などの有料サービスの契約・利用も始めていません。**

元にしたブランチ：feature/inquiry（`6628c18`）。HP原稿の本文・給与・個人情報・秘密情報は、この資料に書いていません。

## 0. まとめ（推奨と着手順）

| 順 | 内容 | 受信処理（doPost）の変更 | Webアプリの新しい版 | 有料サービス | 主な承認 |
|---|---|---|---|---|---|
| 1 | 問い合わせ管理 第1段階の利用開始（予定どおり 11/9 コード反映・11/13ごろ利用開始） | 済み（feature/inquiry） | 必要（予定済み） | なし | 承認済みの手順どおり |
| 2 | **有給の期限案内**（本人へ） | **なし**（1時間ごとの処理から送る） | **不要** | なし（LINE送信数のみ） | 文面・対象・送信開始 |
| 3 | Webhook 中継（Cloudflare Workers・LINE署名の確認）の切り替え | なし（中継側で行う） | 不要 | なし（無料枠） | Webhook URL の変更 |
| 4 | **よくある質問のAI回答** | あり（Inquiry.gs の受付の中） | 必要 | **Claude API（月数百〜3,000円の見込み）** | API契約・ガイドの置き場所・振り分けの言葉・試行 |
| 5 | **新人案内**（入社日から順に配信・確認クイズ） | あり（クイズのボタン） | 必要 | なし（LINE送信数のみ） | 入社日の取り方・配信内容・送信開始 |
| 6 | 第2弾・第3弾：写真・PDFの受付と保存 | あり | 必要 | なし | 保存先・保存期間・受け付ける書類の種類 |

- 2の有給は、受信処理の変更も版の公開も要らないため、いちばん安全に始められます。
- 4・5・6は受信処理（doPost）に手を入れるため、Webアプリの新しい版の公開が必要です。**まとめて1回で公開し**、それぞれの機能は設定（`off`／`record`／`on`）で別々に動かすことをおすすめします。版の公開の回数を減らし、問題が起きたときは設定だけで止められるようにするためです。
- 3の中継は、4（AI回答）を `on` にする前に済ませることをおすすめします。理由は「8. 中継との関係」にあります。

## 1. よくある質問のAI回答

### 1-1. どこで「AI回答／管理本部へ転送」を判定するか

いまの受付の流れ（gas/Inquiry.gs の `INQ_receive_`）は次のとおりです。

1. 重複の確認 → 送り主のプロフィールの確認（友だちでない・偽のデータは案件にしない）
2. 従業員マスタとの照合・機密の言葉の確認・定型連絡（「了解」など）の判定
3. ロックの中で：定型連絡 → 記録だけ／対応中の案件あり → 追記／それ以外 → **新しい案件**
4. ロックの外で：勤怠管理グループ（試行中は管理者）へ通知

**推奨：3で「新しい案件」になるものだけを、AIの対象の候補にします。** 判定は3と4の間（ロックの外）に入れます。

| 条件 | 扱い |
|---|---|
| 定型連絡・スタンプ | 今までどおり記録だけ（AIに送らない） |
| 対応中・未対応の案件がある人の追記 | 今までどおり追記（担当者が対応中のため、AIは口を出さない） |
| 機密の言葉あり（`INQ_hasSecret`） | 転送（AIに送らない） |
| 振り分けの言葉あり（2章） | 転送（AIに送らない） |
| 未登録・確認待ち・重複・退職の人 | 転送（AIに送らない。社員かどうか確かめられないため） |
| 画像・ファイルなど文字以外 | 転送 |
| 上のどれにも当たらない、登録済み・在籍の人の新しい質問 | **AIへ** |

AIの結果：

- **答えられる**（ガイドに根拠がある）：返信（reply）でAIの回答を送り、案件は新しい状態「AI回答済み」で記録します。勤怠管理グループには通知しません。回答の最後に「解決しない場合は『担当者へ』と送ってください」と添えます。
- **答えられない**（根拠なし・判断が必要・AIが転送と判定）：今までどおりの新しい案件として勤怠管理グループへ通知します。
- その後に「担当者へ」と送られたら：その「AI回答済み」の案件を「未対応」に戻して通知します（状態の移り方の例外として、この1か所だけ追加）。

段階的に有効にするため、新しい設定 `INQ_AI_MODE` を設けます。

- 未設定：今と同じ（AIを使わない）
- `record`：AIに回答を作らせるが**送らない**。下書きをシートに残し、管理本部が「送ってよい内容だったか」を確認する（質問した人には今までどおり担当者が対応）
- `on`：AIの回答を返信する

### 1-2. 返信の期限内にClaude APIの回答を返せるか

公式資料で確認した条件：

- LINEの返信トークンは1回だけ使えます。**受信から1分以内**に使う必要があります（1分を過ぎると動く保証はありません）。
  出典：[Messaging API リファレンス（Send reply message）](https://developers.line.biz/en/reference/messaging-api/#send-reply-message)
- Apps Script の1回の実行は最大6分です。外部へのURL取得（UrlFetchApp）は無料アカウントで1日20,000回、Workspaceで100,000回です。公式資料に、URL取得1回の待ち時間の上限の記載はありません。
  出典：[Apps Script の割り当て](https://developers.google.com/apps-script/guides/services/quotas)
- LINEには「入力中」の表示（読み込みのアニメーション）を出すAPIがあります。5〜60秒（5秒きざみ）で指定でき、この表示は送信数に数えません。
  出典：[Messaging API リファレンス（Display a loading animation）](https://developers.line.biz/en/reference/messaging-api/#display-a-loading-animation)

見込み：ガイドの抜粋（数万字）を添えて質問しても、Claude API の回答は通常十数秒以内に返ります。そのため、1分の期限内に返信できる見込みです。ただし、確実にするため次のようにします。

- APIを呼ぶ前に「入力中」の表示を出す（無料）。
- 時間を区切る：**受信から40秒**を過ぎたらAIの回答を使わず、転送に切り替える。
- **失敗したら必ず人に回す**：APIのエラー・時間切れ・形式が違う回答・設定がない、のどれでも「新しい案件として通知」にする。質問した人に「AIが失敗しました」とは送らない。
- エラーは今の仕組み（`AC_adminNotice_('inquiry', …)`、1日1回）で管理者に知らせる。
- APIを呼んでいる間はロック（`LockService`）を持たない。同じ時間に届いたほかの受信（社員番号登録・ToTの取り込みなど）を待たせないためです。
- 2回目の送信（再送）は使わない。LINEの再送で同じ質問が2回届いても、今の重複の確認（`webhookEventId`）で1回だけ処理します。

### 1-3. AIの回答を案件として記録する方法

問い合わせ専用のスプレッドシート（`INQ_SPREADSHEET_ID`）に記録します。従業員マスタには書きません。

- 「問い合わせ」シート：今の列に「AI回答済み」の状態を足します。列は増やしません。
- 「やりとり」シート：種類「AI回答」の行を足します。内容は回答の本文、そしてガイドの版と根拠の見出し（どの項目を元に答えたか）です。
- 新しい「AI記録」シート：日時・案件番号・判定（回答／転送・理由）・使ったモデル・かかった秒数・入力と出力のトークン数・ガイドの版を記録します。費用の確認と、誤った回答の追跡に使います。**AIに送った文面（伏せたあと）も残す**ので、何を外部に送ったか後から確かめられます。
- `record` のときは、回答を「下書き」として同じ所に残し、「送信」欄を「送らない（記録のみ）」にします。

## 2. AIに送る前の振り分けと、送らない情報

### 2-1. 管理本部へ回す質問の判定

**AIに送る前に、Apps Script の中で言葉で判定します**（AIの判断に任せない）。当たったものはAIに送らず、そのまま転送します。

| 分類 | 言葉の例（既定） |
|---|---|
| 給与 | 給与、給料、時給、日給、月給、手当、残業代、支給額、明細、源泉、年末調整、税金 |
| 口座 | 口座、銀行、振込、振り込み |
| マイナンバー | マイナンバー、個人番号 |
| 健康 | 健康、病気、通院、診断、ケガ、怪我、妊娠、障害、メンタル |
| 評価・昇給・賞与 | 評価、査定、昇給、昇格、降格、賞与、ボーナス |
| 懲戒 | 懲戒、処分、始末書、減給、解雇 |
| 雇用条件 | 契約、雇用条件、労働条件、更新、雇止め、退職金、社会保険、扶養 |

- 言葉の一覧は、今の `INQ_SECRET_WORDS` と同じように、新しい設定 `INQ_AI_BLOCK_WORDS` で管理本部が足せるようにします。
- 判定は「含まれていたら転送」にします。言葉で拾いきれない質問のために、**AIへの指示でも同じ分類を「答えずに転送」と決めておきます**（二重の守り）。AIが「転送」と返したら転送します。
- 迷うときは転送する側に倒します。AIが答えすぎるより、人が答えるほうが安全なためです。

### 2-2. 氏名・社員番号・長い数字をAIへ送らない方法

AIに送る直前に、本文を次のように置き換えます。置き換えた文面だけを送り、元の文面は送りません。

| 対象 | 置き換え |
|---|---|
| 7桁以上の数字（半角・全角、間のハイフン・空白を含む） | `［数字］` |
| 社員番号・TOTコードと同じ数字（桁数によらず。従業員マスタから） | `［番号］` |
| 従業員マスタの氏名・別表記、LINE表示名（全員分。姓だけ・名だけも） | `［氏名］` |
| 電話番号・メールアドレス・郵便番号の形 | `［連絡先］` |
| 機密の言葉（`INQ_SECRET_WORDS`） | 当たったら、そもそも送らない（2-1） |

- AIには、LINEのユーザーID・社員番号・氏名・所属を**一切渡しません**。渡すのは「伏せたあとの質問文」と「ガイドの抜粋」だけです。
- 置き換えたあとの文面が短すぎる（伏せた部分ばかり）ときは、AIに送らず転送します。
- 置き換えは純粋関数（Apps Script の外でテストできる関数）にし、架空の氏名・番号でテストします。

## 3. 回答の根拠（ガイド原文）の置き場所と更新手順

このリポジトリは公開設定のため、**ガイドの本文はリポジトリにもコードにも置きません。**

### 推奨：Googleドライブの非公開の Google ドキュメント「AI回答用ガイド（抜粋）」

- 従業員HPの確定原稿（Claudeのドキュメント「REBIRTH 従業員HP 設計案・確定原稿」）から、**AIが答えてよい部分だけ**を写したドキュメントを別に作ります。
  - **給与テーブル・懲戒基準は写しません。** 2-1の「人に回す」分類と同じ内容を、AIが答えられないようにするためです。
  - 先頭に「版：YYYY-MM-DD」の1行を置きます。AIの回答の記録に、この版を残します。
- 所有者は Apps Script を動かしているアカウントにします。共有は管理本部の編集者だけにします（リンクでの共有はしない）。
- Apps Script は、新しい設定 `INQ_AI_GUIDE_DOC_ID` に書いたドキュメントを読み、本文を一時記憶（6時間）します。ドキュメントのIDだけが設定に入り、本文はリポジトリに入りません。
- ほかの案との比較：

| 置き場所 | 評価 |
|---|---|
| Google ドキュメント（非公開）**（推奨）** | 管理本部が普段の操作で直せる。変更履歴が残る。Apps Script から読める |
| スプレッドシートの1シート（質問と答えの表） | 決まった質問には向くが、HPの文章をそのまま使いにくい。将来の「よくある質問の一覧」として併用は可 |
| スクリプトプロパティ | 1つの値の大きさに制限があり、管理本部が直しにくい。不向き |
| Claudeのドキュメントを直接読む | Apps Script から読む手段がなく、権限の管理も別になる。不向き |

### 管理本部が更新する手順（案）

1. 「AI回答用ガイド（抜粋）」を開いて直す。先頭の「版」の日付を今日にする。
2. Apps Script で `INQ_aiGuideCheck` を実行する（新しく作る関数。本文は表示せず、版・文字数・最終更新日だけを表示し、一時記憶を消す）。
3. 次の質問から新しい内容で答える。
4. HPの確定原稿を直したときは、同じ日に抜粋も直す（手順書に書く）。

## 4. 有給の期限案内（本人へ）

### 今ある仕組み

- 有給の年5日の確認はすでにあります（`AC_paidLeaveStatus`・`AC_paidLeavePeriod`・`AC_paidLeaveCheck`）。
  - ToTのデータは、VPSが**月曜の朝だけ**取り込みます（過去1年分の有休の日と、入社日 `hiredDate`）。
  - 基準期間は入社から6か月後の日から1年ごとです。期限まで120日以内で5日に足りなければ「注意」、60日以内なら「急ぎ」になります。
  - 結果は従業員マスタの「有給5日」シートに書かれ、**管理者だけ**に知らせています。
- 本人への送信の仕組みもあります（管理本部の本人へのお知らせ、`AC_selfNoticesHourly_`）。
  - 1時間ごとの処理から送るため、**受信処理と版の公開は要りません**。
  - 段階的な設定（未設定／`record`／`on`）があります。`on` は `DRY_RUN=false` のときだけ送ります。
  - 「お知らせ停止」の人を除く処理、同じ日に2回送らない記録（`sent:…`）もあります。

### 推奨の実装

- 新しい設定 `PAID_LEAVE_SELF_NOTIFY`（未設定／`record`／`on`）を足し、`AC_selfNoticesHourly_` から呼びます。
- 月曜の朝のデータ（`tot-latest.json` に有休のデータ `paidLeaves` があるとき）だけ判定します。
  - ToTの有休データが一部でも読めなかった日は送りません（今の管理者向けと同じ条件）。
- **対象者**（`AC_selfNoticeTargets` と同じ考え方で、所属の条件だけ外したもの）：
  - 従業員マスタで在籍、退職日の前、「LINE確認済み」、TOTコードが1人に決まる人
  - 「お知らせ停止」の期間中の人は除く（範囲「全部」「勤怠のみ」のどちらでも除く）
  - 有給の判定が「注意」（期限まで120日以内）または「急ぎ」（60日以内）の人
- **送る回数**：1人につき、1つの基準期間で「注意」になったとき1回、「急ぎ」になったとき1回の、**最大2回**。
  - 毎週は送りません。記録は送信の記録（`AC_state_`）に「期間の開始日＋段階」で残します。
- 文面は「LINE文面」シートで上書きできるようにします（今の仕組み `AC_templateOverrides_`）。
  - 本文に入れるのは期限の日と「あと何日」だけです。取得日数の内訳は書きません。
- 本人に送った人は、管理者向けの一覧にも「本人に案内済み」と出します。

### 送信数

- 本人へのプッシュ1通は1人分として数えます。
- 1年で1人最大2通です。対象になる人数は「有給5日」シートの「状況」欄の数で決まります。
  - 例：月に5人が「注意」または「急ぎ」になる場合、月5〜10通です。
- `record` で1〜2週間記録し、実際の人数を確かめてから `on` にします。

## 5. 新人案内（入社日から順に配信・確認クイズ）

### 入社日の取り方

| 取り方 | 状況 | 評価 |
|---|---|---|
| 従業員マスタのO列「入社日」 | 社員管理AI（feature/employee-admin・未導入）が「入社」の申請の承認で書く予定。今の本番のマスタには列がない | **推奨**（社員管理AIの導入後）。入社前からわかる |
| ToTの `hiredDate` | VPSが月曜の朝だけ取り込む（有給の確認用） | 補助。ToTへの登録が遅れると届かず、週1回しか更新されない |

- 推奨：O列を使い、O列が空の人だけ ToT の `hiredDate` で補います。両方あって違う場合は送らず、管理者に知らせます。
- 社員管理AIを先に入れない場合は、管理本部がO列に手で入社日を入れる運用になります。

### 順番に配信する方法

- 新しいファイル `gas/Onboarding.gs` に処理をまとめます（Inquiry.gs と同じく、既存のファイルに手を入れる場所を最小にするため）。
- 配信の予定は、非公開の Google スプレッドシート「新人案内」で管理本部が決めます（リポジトリには書きません）。
  - 列：段（1〜）・入社日から何日目・送る時刻・本文・クイズ（問い・選択肢・正解）
- 毎朝の既存の時刻の処理、または新しい1日1回の時刻の処理（例 9:00）で判定します。
  - 判定：今日が「入社日＋N日目」になった人に、その段を送ります。
  - 送信は1時間ごとの処理と同じ方式で、**受信処理と版の公開は要りません**（クイズのボタンを押した後の処理だけ受信処理が要ります）。
- 対象：在籍、「LINE確認済み」、「お知らせ停止」中でない、入社日から決めた日数（例 30日）以内の人。
  - LINE登録がまだの人は、登録した日以降に、まだ送っていない段から送ります（さかのぼって全部は送らない。最大1段だけ）。
- 送信の記録（`onb:社員番号:段`）で、同じ段は1回だけ送ります。
- 設定 `ONB_MODE`（未設定／`record`／`on`）で段階的に始めます。

### 確認クイズ（postback）

- 1問ごとに、選択肢のボタン（postback）をつけて送ります。押した結果の返信（正解・解説）は返信なので、送信数に数えません。
- postback の中身（300文字まで）：`onb|1|段|問|選択肢|合言葉6桁`
  - 合言葉は、その人・その段ごとに作ってシートに保存します。他人のボタンや偽のデータを受け付けないためです（問い合わせのボタンと同じ考え方）。
  - 押した人のLINEユーザーIDが、送った相手と同じかを確かめます。
- 1回目の答えだけを記録します（2回目以降は「回答済みです」と返信）。

### 問い合わせのボタンと衝突しない設計

- 今の受信処理では、1対1の postback はすべて `INQ_onUserEvent_` に渡されます。
  - Inquiry.gs は `inq|1|` で始まるものしか受け付けません（`INQ_parsePostback`）。始まりの違う `onb|1|` は無視するので、**問い合わせ側は誤作動しません**。
- 受信処理の1対1の postback の行を、先頭の文字で振り分けるようにします（`inq|` → 問い合わせ、`onb|` → 新人案内）。
  - 変える行は1か所で、関数が無ければ何もしない今の書き方を守ります。
- 社員管理AIは postback を使いません（クイック返信の文字）。勤怠管理グループでのみ動くため、1対1の新人案内とは重なりません。
- クイズのボタンを押すと、受信処理に postback が届きます。問い合わせの案件にはしません（今も postback は案件にならない作り）。

### 結果を勤怠管理グループへ知らせる方法

- グループへのプッシュは**グループの人数分**数えます。そのため、1回答ごとに知らせず、**1日1回のまとめ**（例 17:00、その日に終わった人・答えがまちがっていた問いがある人だけ）にします。
- 内容：社員番号・氏名・終わった段・正解数。答えの内容は送りません。
- 試行の間は管理者だけに送ります（`ONB_NOTIFY_TO=admin`、問い合わせと同じ考え方）。

### 送信数

- 新人1人につき段の数（例 5段なら5通）、そして勤怠管理グループへのまとめ（グループの人数×まとめの回数）。
- 例：月2人入社・5段 → 本人へ10通。まとめは月に数回 × グループの人数。

## 6. 写真・PDF（第2弾・第3弾の前提）

### LINEで受け取った写真・PDFの取り方と、LINE側の保存期間

公式資料（[Messaging API リファレンス：Get content](https://developers.line.biz/en/reference/messaging-api/#get-content)）より：

- 受信処理に届くのは「メッセージID」だけです。画像・動画・音声・ファイル（PDFなど）の中身は、`GET https://api-data.line.me/v2/bot/message/{messageId}/content` で取り出します（いつもとは別のドメイン）。
  - 取り出せるのは `contentProvider.type` が `line` のときだけです。
- 大きい動画・音声は準備中の間は `202` が返り、取り出せません。
- ファイルの受信には、ファイル名とファイルの大きさが付きます。
- **LINE側の保存期間：「送信から一定の期間が過ぎると自動で削除されます。どのくらいの期間保存されるかは保証しません」**と書かれています。期間の数字は公式資料にありません。
  - そのため、**受信したらすぐに取り出して保存**する必要があります。後でまとめて取り出す方式は使えません。

### 受信したときにGoogleドライブの閲覧者限定フォルダへ保存する方法

- 今は、画像・ファイルは問い合わせの案件に「（画像）」「（ファイル）」と記録するだけです（`INQ_messageSummary`）。中身は取り出していません。
- 推奨：
  1. Googleドライブに保存用のフォルダ「LINE受付書類」を作ります。共有は管理本部の閲覧者・編集者だけにします（リンクでの共有はしない）。フォルダのIDは設定 `INQ_FILE_FOLDER_ID` に入れます。
  2. 受信処理で画像・ファイルを受けたら、上のAPIで中身を取り出してフォルダに保存します。
     - ファイル名：`案件番号_受信日時_種類`。氏名は名前に入れません。
  3. 「やりとり」シートに、ドライブのファイルIDとリンクを残します。勤怠管理グループへの通知には**リンクを載せず**「書類あり」とだけ書きます（グループの全員が見られるため）。
  4. 取り出しに失敗したとき（`202`・エラー）は「取り出し待ち」の表に入れ、1時間ごとの処理で数回やり直します。最後まで取れなければ管理者に知らせ、本人に再送をお願いします。
- 受け付けるのは、画像とPDFだけにすることをおすすめします。動画・音声は受け付けず、案件の記録だけにします。
- **マイナンバーの書類は、LINEでは受け付けないことをおすすめします。** マイナンバーは扱い方の決まり（安全管理措置）が厳しく、LINEとドライブの両方に残るためです。案内の文面で、別の方法で出すよう伝えます。

### 書類ごとの削除のしかた

- 案件番号（またはファイルID）を指定して実行する削除の関数（例 `INQ_deleteFile`）を作ります。
  - ドライブのファイルを削除し、シートのリンクを「削除済み（日時・削除した人）」に置き換えます。
  - 実行した記録を「やりとり」シートに残します。
- ドライブの削除は、まずゴミ箱に入ります。ゴミ箱から完全に消すには、ドライブのAPI（拡張サービス）を使うか、管理本部がゴミ箱を空にします。
- 保存期間（例：案件が「対応済み」になってからN日で自動削除）を決めていただければ、1日1回の処理で自動で削除します。

## 8. 社員管理AI・Webhook中継との関係と、着手の順番

### 今の状況

- 社員管理AI（feature/employee-admin・未マージ）：勤怠管理グループで「入社」「退社」「取消」を受け付け、従業員マスタに反映する仕組みです。
  - **Claude API は使っていません**（決まった形の文字を読む作り）。今回のAI回答とは別の仕組みです。
  - 従業員マスタにO列「入社日」を足す予定で、新人案内（5章）の入社日の元になります。
- Webhook中継（Cloudflare Workers）：LINEの署名を確かめ、正しいものだけを既存の Apps Script へ転送します。勤怠管理グループのイベントは、社員管理AIにも送ります。
  - 記録では、10/27 時点で Webhook はまだ切り替えていません。
  - 1対1のトークのイベントは、既存の Apps Script にだけ届きます。そのため、AI回答・新人案内・写真の受付は**既存の Apps Script（Inquiry.gs など）の中で作ればよく、中継のコードは変えなくて済みます**。

### AI回答の前に中継を入れる理由

- Webアプリの受け口（URL）は誰でも送れます。LINEの署名を確かめない今のままだと、偽のデータを送られる可能性があります。
  - 今の問い合わせ管理はプロフィールの確認（友だちでないIDは案件にしない）で守っています。AI回答も同じ確認の後に呼ぶため、偽のデータで Claude API の費用が増えることは起きにくい作りです。
  - それでも、**有料のAPIを呼ぶ入口は署名で守るほうが安全**です。また、中継は失敗した転送を最大24時間やり直すため、受信の取りこぼしも減ります。
- 中継は応答に最大28秒待ちます（`AbortSignal.timeout(28000)`）。AI回答は40秒で打ち切る案（1-2）なので、中継の待ち時間を超えることがあります。
  - 中継は LINE への応答の後も処理を続ける作り（`waitUntil`）です。ただし、28秒を過ぎると中継から見て「失敗」になり、**同じイベントを再送**します。再送されても今の重複の確認で1回だけ処理しますが、無駄な再送を避けるため、**AIの打ち切りを25秒にする**か、中継の待ち時間を延ばすかを、実装のときに決めます。推奨は「AIは25秒で打ち切り、転送に切り替える」です。

### 着手の順番（案）

1. 問い合わせ管理 第1段階を予定どおり利用開始（11/9 コード反映、11/13ごろ利用開始）。2週間ほど様子を見る。
2. 有給の期限案内を実装 → `record` で記録 → `on`（受信処理・版の公開なし）。
3. 社員管理AIと中継の導入（Webhook の切り替え）。これで署名の確認と入社日（O列）がそろう。
4. AI回答と新人案内を1つの版にまとめて実装し、Webアプリの新しい版を1回だけ公開する（どちらも未設定＝今と同じ）。
   - AI回答：`record`（下書きだけ・2週間）→ 管理者だけで `on` → 全員に `on`
   - 新人案内：`record` → 次の入社の人から `on`
5. 写真・PDFの受付（第2弾）は、保存先と保存期間を決めてから実装する。

## 11. テスト項目の提案（実装の方針が決まったら・すべて架空データ）

今回はテストを作っていません。方針が決まったら、次の項目を `npm test`（模擬環境・架空データ）で作ります。

**AI回答**

- 振り分けの言葉が含まれる質問は、AIを呼ばずに転送される（分類ごとに1件以上）
- 機密の言葉・未登録・確認待ち・退職の人・画像は、AIを呼ばない
- 7桁以上の数字・社員番号・氏名（姓だけ・名だけ）・表示名・電話・メールが伏せられ、AIに送る本文に残らない
- AIが「回答」を返す → 返信が1回だけ送られる、グループには通知しない、案件が「AI回答済み」
- AIが「転送」を返す・エラー・時間切れ・形式違い・APIキーなし → 今までどおり新しい案件として通知され、本人には何も送らない
- `record` では返信を送らず、下書きだけが残る
- 「担当者へ」で「未対応」に戻り、通知される
- 同じイベントが2回届いても、AIは1回だけ呼ばれる
- 1日の上限件数を超えたら転送になる
- 対応中の案件がある人の追記では、AIを呼ばない

**有給の期限案内**

- 「注意」「急ぎ」で1回ずつ、同じ段階は2回送らない
- お知らせ停止・LINE未確認・退職・TOTコードの重複の人には送らない
- 有休データが一部読めなかった日は送らない
- 月曜以外のデータでは何もしない

**新人案内**

- 入社日＋N日目に、その段だけが送られる。同じ段は1回だけ
- O列と ToT の入社日が違う人には送らず、管理者に知らせる
- 他人のボタン・合言葉違い・古い段のボタンは受け付けない
- `inq|` のボタンは問い合わせに、`onb|` のボタンは新人案内に届き、互いに影響しない
- グループへのまとめは1日1回

**写真・PDF**

- 受信したらすぐ取り出して保存し、リンクがシートに残る。グループへの通知にリンクが載らない
- `202`・エラーのときは「取り出し待ち」に入り、やり直しで保存される
- 削除の関数でファイルが消え、シートが「削除済み」になる
- 動画・音声は保存しない
