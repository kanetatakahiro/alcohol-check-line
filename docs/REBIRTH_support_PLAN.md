## 0. 結論

1. **土台はあります。** 問い合わせの受付・記録・重複防止・ボタンでの引受け（対応します／対応済みにする）・9時と15時のまとめ・機密を伏せる処理・キーワードでの分類は動いています（gas/Inquiry.gs）。
2. **足りないのは「AIの回答」の部分です。** FAQでの返信・解決確認・無回答の処理・引継ぎ・緊急通知・AIの状態の記録を作ります。どれも Inquiry.gs の中で作れて、コード.gs はほとんど変えません。
3. **回答はテンプレート型です**（外部のAIは使わない・費用0円）。返信は replyToken を使うため、**LINEの送信数は増えません**。
4. **勤怠・アルコールチェック・希望休・夜の本人通知は止まらない作りです。** これらは時刻のトリガーかVPSからの取り込み（tot-raw）で動き、問い合わせの道を通りません。有人対応の判定は問い合わせの受付（`INQ_receive_`）の中だけに入れます。
5. **免許証・貸与品・退職案内は、従業員マスタとは別のタブにします**（O列は入社日に使う予定のため）。
6. 11/13 の前の小さな修正（要注意の分類・ハラスメントの本文をグループに出さない）は、**Inquiry.gs 版 2026-11-10c として作成済み**です（本番未導入）。

### 受け口の流れ（doPost）

```
LINE → doPost（コード.gs・署名の確認なし。Workersは使っていない）
 ├ tot-raw → AC_handleTotRaw_（勤怠の取り込み・夜の本人通知）            … 問い合わせとは別。止めない
 └ events → AC_handleEvent_
     ├ グループ → AC_handleGroupEvent_（部門登録・問い合わせのボタン INQ_onGroupPostback_）
     ├ 友だち追加 → 案内の返信
     ├ 社員番号だけの文字 → LINE登録（従業員マスタのF〜I列）
     └ それ以外（文字・画像・スタンプ・本人のボタン） → INQ_onUserEvent_ → INQ_receive_
           重複（受信記録）・実在の確認（LINEのプロフィール）・定型連絡（出勤・退勤など）は記録だけ
           その人に未完了の案件がある → 追記として記録（対応中なら30分に1回、担当へ知らせる）
           ない → 新しい案件（未対応）。INQ_MODE=on ならグループへボタン付きで知らせる
時刻のトリガー：アルコールチェックの案内・催促／飲酒検知（10分ごと）／1時間ごとの取り込み（alcoholCheckImportTot。分類・要点を埋める）／
                希望休の案内（毎月10日）／夜の見守り（22:45）／問い合わせのまとめ（INQ_remind 9時・15時）
```

## 6. 有人対応の停止と再開

```
本人のメッセージ → INQ_receive_
   重複・実在の確認・定型連絡（今と同じ）
   緊急の判定（第9章） → 当たれば緊急通知（有人対応中でも）
   その人の案件の状態は？
     未対応・対応中（＝引継ぎ後〜対応完了の前） → 追記として記録。AIは返信しない（停止）
     AI対応中                                → 解決確認への返事・追加の質問への答えとして扱う
     なし（対応済み・AI解決済み・無回答だけ）  → 新しい案件として、FAQで回答（AI対応中）
```

- **停止**：引継ぎで状態が「未対応」になったとき。「やりとり」に「AI停止（引継ぎ）」を記録します。
- **再開**：担当が「対応済みにする」を押したときだけ（D7）。「やりとり」に「AI再開」を記録し、次のメッセージから新しい案件としてFAQで答えます。自動では戻しません。
- **止めないもの**：アルコールチェック・勤怠の本人通知・希望休・社員番号の登録・夜の本人通知。どれも `INQ_receive_` を通らないので、判定の影響を受けません（テスト12・13・27）。
- **有人対応中に別の件が届いたとき**（仕様 3-2・19-1）：同じ案件の追記として記録します。担当への追記の通知（30分に1回まで・今と同じ）に「別件の可能性（分類：○○）」を添えます。緊急の言葉が当たれば、緊急通知は送ります。
- LINE公式アカウントのチャット画面でスタッフが返信しても、システムはその内容を読めません。そのため有人対応中かどうかは、ボタンの状態だけで判断します。

## 8. 緊急通知の判定と送り方

**判定**（本文の全体。機密を伏せた後の本文で判定。言葉は定数にして、後から足せるようにする）：

| 種類 | 判定の案 |
|---|---|
| 給与未入金 | 「給与・給料・振込・振り込み」のどれか**と**「入っていない・入金されていない・振り込まれていない・未入金・届いていない」のどれか |
| 社用車の事故 | 「事故・追突・ぶつけ・当て逃げ・物損」 |
| 勤務中のケガ | 「ケガ・けが・怪我・負傷・骨折・出血・救急・やけど・火傷」 |

- 質問の形（例：「事故のときはどうすれば？」）でも緊急として扱います（取りこぼさない側）。誤って当たった件は、担当が「対応済み」にして終えます。
- 実在の確認（LINEのプロフィールが取れる人だけ）を必ず通します。署名の確認がないため、偽のデータでの誤った通知を防ぐためです。

**送り方**（D2：時間帯に関係なく、すぐ）：

- 新しい案件が緊急のとき：グループへの受付時のお知らせの題を「【緊急・問い合わせ】」にし、同時に管理者の個人LINEへ文字だけで送ります。
- 未完了の案件への追記が緊急のとき：グループと個人LINEの両方へ短いお知らせを送ります。
- 送り先ごとに「通知送信履歴」に記録し、片方の失敗で止めません（飲酒検知の `AC_alertSend_` と同じ形）。同じ案件には1回だけです（「緊急通知日時」の列）。
- 文面には種類（給与未入金・事故・ケガ）と名前（所属）だけを出し、本文は「チャットで確認してください」とします。
- 本人へは、仕様書の文面案（6-3・10-3・13-2。深刻な内容は絵文字なし）を返信します（0通）。

## 9. 免許証の更新報告（LINEで受け取る・D12）

```
30日前・7日前の通知（push）：「更新したら、このトークに『免許更新』と送ってください」
本人「免許更新」 → 返信：免許証の画像を送ってください（10分間、受付中にする）
本人 画像 → LINEから画像を取得して Drive の管理本部だけのフォルダへ保存（ファイル名は社員番号と日付だけ）
         → 返信：有効期限を選んでください（日付を選ぶボタン）

         → 管理本部が画像を見て「確認済み」にする
```

- **本人の確認**：従業員マスタで「LINE確認済み」の人だけ受け付けます。それ以外は保存せず、問い合わせとして扱います（17：識別が不確かなら個別の情報を出さない）。
- **誤登録の防止**：期限が過去の日付・今の期限より前・10年より先なら受け付けず、もう一度選んでもらいます。画像だけで期限が来ないとき（10分）は「保留」とし、管理本部が確かめます。
- **受付中でない画像**は、今までどおり問い合わせになります。
- **保存先と権限**：Drive のフォルダ（プロパティ `LICENSE_FOLDER_ID`。管理本部だけに共有）。Apps Script はすでに Drive を使っているので、新しい権限の許可は要りません。
- **削除**：退職日から1年たった人の画像を、毎日の処理で削除します（D17）。
- **呼び出しの場所**：新しいファイル License.gs に入れ、Inquiry.gs の `INQ_onUserEvent_` の最初で呼びます。コード.gs は変えません。受付は doPost で動くので、Webアプリの版の公開が必要です（7b）。
