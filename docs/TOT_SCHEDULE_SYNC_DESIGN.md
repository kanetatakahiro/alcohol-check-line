# 勤怠変更連絡フォームの承認 → Touch On Time のスケジュールへの自動反映（設計メモ）

- 作成：2026-11-13（11/13 安藤さんの要望）。**調査と設計だけ**です。実装・Touch On Time（ToT）への書き込み・本番の Apps Script・VPS は触っていません。
- 更新：2026-11-13。**実装しました**（gas/TotSync.gs・src/tot-write.js・コード.gs 版 2026-11-13c・**本番未導入**）。決まったことと実装の内容は「9. 実装（版 2026-11-13c）」。1〜8 は設計のときの記録として残します。
- 対象：勤怠連絡フォームの「欠勤」「有給休暇」「休みの変更（シフト交換など）」。管理本部が LINE グループのボタンで承認したら、ToT の日別スケジュールに反映する。
- 対象外：「休日出勤」「打刻の修正」（本人が ToT で申請する）。遅刻・早退・その他も対象外。
- 打刻のお知らせの【勤怠の変更】の文（コード.gs 版 2026-11-13b）は、自動反映ができるまでのつなぎ。

## 0. 結論（先に）

1. **書き込みは VPS の中継から行う**。ToT のトークンには許可IPの設定があり（README）、今のトークンは VPS（133.167.110.249）からだけ使える。Apps Script は送信元のIPが決まらないので ToT に書き込めない。トークンを Apps Script に置く必要もなくなる。
2. **ToT 側で先に確かめることが3つある**（これが分かるまで実装しない）：
   - 今のトークンの「連携希望項目」に「日別スケジュールデータ（書き込み）」が入っているか（入っていなければサポートセンターへ追加を依頼）
   - 会社の「全日休暇の取得方法」がパターン使用か（パターン使用なら、有給・欠勤の全日休暇は API で登録できない）
   - 「欠勤」が休暇区分にあるか（休暇区分データ GET /holiday-types で確かめる）
3. **流れ**：フォーム送信 → 勤怠管理グループに承認ボタン → 押されたら「反映待ち」に → VPS が数分ごとに反映待ちを取りに来て ToT に書き込み → 結果をグループへ。反映前のスケジュールを保存して「元に戻す」ボタンも付ける。
4. **休みの変更**は、2つの日のスケジュールを入れ替える（シフト交換）のを基本にする。
5. **打刻がある日は ToT がエラーにする**ので、過ぎた日・出勤した日は自動反映しない（本人のスケジュール申請に戻し、【勤怠の変更】の文はそのまま送る）。

## 1. API（https://developer.kingoftime.jp/ の原文で確認）

資料のページ（HTML）を取得し、原文で確かめた内容だけを書きます。

### 1-1. 日別スケジュールデータの登録・更新

- `PUT /daily-schedules/{employeeKey}/{date}` …「日別スケジュールデータを登録・更新(既存スケジュールを削除後に登録)する。」
  - **既存のスケジュールを消してから登録する**。送らなかった項目（休憩・出勤先など）は消える。
- 一括：`PUT /daily-schedules`（`employeeScheduleRequests: [{ employeeKey, dailySchedules: [{ workingDate, … }] }]`、1リクエスト1,000件まで。応答は `successRequest`・`errorRequest`（日ごとの `code`・`message`））
- 削除：`DELETE /daily-schedules/{employeeKey}/{date}`（成功は 204）
- 注意（原文のまま）：
  - 「※dateで指定された勤務日に対して、既に打刻・勤怠補助項目が存在する場合にはエラーとなります。」（登録・更新・一括・削除のすべて）
  - 「※全日休暇の登録・更新について、企業の全日休暇の取得方法がパターン使用の場合には対応していません。」
  - 締め済みの日の扱い：**書いていない**
- 送る項目（リクエスト定義の原文）：

| 項目 | 説明（原文） |
|---|---|
| workPlaceDivisionCode | 出勤先所属コード(※未指定の場合：指定した従業員の所属コード) |
| clockInSchedule / clockOutSchedule | 出勤予定時間 / 退勤予定時間（例 `2016-05-01T09:00+09:00`） |
| workFixedStart / workFixedEnd | 勤務開始刻限 / 勤務終了刻限 |
| startEndBreakSchedule | 休憩開始終了予定（`[{ start, end }]`） |
| fulltimeHoliday | 全日休暇（`{ code: 休暇区分コード }`） |
| halfdayHolidays | 半日休暇（`[{ typeName: AM半休／PM半休, code }]`） |
| hourHolidays | 時間休暇（`[{ start, end, code }]`） |
| workDayTypeCode | 勤務日種別コード(1:平日,2:法定休日,3:法定外休日)(※未指定の場合：1:平日) |
| note | 備考 |

- **勤務パターン（スケジュールパターン）を指定する項目は無い**。出勤・退勤の予定時刻と休憩を直接送る。パターンは取得側の `additionalFields` の `schedulePatternCode`・`schedulePatternName` で読めるだけ。勤務パターンの一覧を取る API も無い。
- **休日区分**は `workDayTypeCode`（1 平日／2 法定休日／3 法定外休日）。取得側は `workDayTypeName`（名前）で返るので、元に戻すときは名前→コードに読み替える。
- **全日有給**は `fulltimeHoliday: { code: 有休の休暇区分コード }`。コードは「システムで自動採番されるコードです（変更不可）。KING OF TIMEの管理画面では確認できないため、休暇区分データを取得しご確認ください。」

### 1-2. 休暇区分データ

- `GET /holiday-types` → `[{ code, name }]`（例：`{ "code": "1", "name": "有休" }`、`{ "code": "2", "name": "代休" }`）
- 使い方：最初に1回取得して「有休」「欠勤」（あれば）のコードを控える（設定に保存）。コードは変わらないが、休暇区分を増やしたときは取り直す。

### 1-3. 申請（参考：別の自動化の道）

- スケジュール申請の状態は `applying`（申請中）／`rejected`（棄却）／`approved`（承認）（原文。今まで未確認だった「却下」の値は `rejected`）
- `PUT /requests/{requestKey}`（`administratorKey` 必須・`approve: true/false`・`adminComment`）で、**本人が出した申請を API で承認・棄却できる**。「管理者識別キーで指定した管理者が対象の申請の承認フローに存在しない、または承認レベルが異なる場合にはエラー」。
- 申請を代わりに新しく出す API（POST）は無い。

### 1-4. 利用の制限（原文）

- 利用禁止の時間帯：8:30〜10:00・17:30〜18:30（アクセストークンと打刻登録以外のすべての API）
- 「リクエストは並列で同時に送信しないでください。1件ずつ送信し、目安として1秒ほど送信間隔を空けてください。」
- 企業単位で直近5分に500リクエストまで（超えると HTTP 403・code 105）。サーバーの負荷で HTTP 429（code 303・308）
- 書き込みに使える項目はトークンの「連携希望項目」で決まる（「日別スケジュールデータ（書き込み）」＝ PUT/DELETE）。トークンの発行・変更はサポートセンターへ依頼。

## 3. 「休みの変更」の出勤の日の勤務パターン（案）

フォームの「日付（開始日）」＝もともと休みの日（出勤に変える）、「変更後の休みの日」＝新しく休む日（もともと出勤の日）。

- **案A（おすすめ）：2つの日のスケジュールを入れ替える（シフト交換）**
  - もともと休みの日 ← 変更後の日の今のスケジュール（出勤・退勤の予定時刻、休憩、出勤先所属、勤務日種別＝平日）
  - 変更後の日 ← もともと休みの日の今の勤務日種別（法定休日・法定外休日）で、時刻なし
  - よい点：時刻を推測しない。勤務日種別（法定休日の数）も週の中で変わらない。元に戻すのも入れ替え直すだけ
  - 承認のカードに「11/12（木）：休み（法定外休日）→ 9:00-18:00 の出勤（11/15 の予定をそのまま）／11/15（日）：9:00-18:00 → 休み（法定外休日）」と出し、押す人が確かめられるようにする
- 案B：その人の当月で一番多い出勤の予定時刻を使う（変更後の日も休みだった、など入れ替えられないとき）。承認のカードに「推定」と出す
- 案C：反映しない（ボタンで「反映しない」を選び、本人のスケジュール申請にする）
- 入れ替えができない（変更後の日に出勤の予定時刻が無い・2つの日が離れすぎ〔例：14日超〕・月をまたいで締め済み）ときは、案Bか案Cを承認のカードで選べるようにする

## 4. 制限への対応（案）

| 制限 | 対応 |
|---|---|
| その日に打刻・勤怠補助項目があるとエラー | 書き込む前に VPS がその日の日別打刻（GET /daily-workings/timerecord）を確かめ、打刻があれば書き込まずに「失敗（打刻あり）」。休みの変更の「もともと休みの日」はその日に出勤するので、**当日より前に承認・反映する**運用にする（承認のカードに「○日までに承認してください」）。過ぎた日・出勤済みの日は、本人のスケジュール申請に戻す（【勤怠の変更】の文で依頼） |
| 全日休暇がパターン使用の会社は非対応 | 管理本部に ToT の設定（全日休暇の取得方法）を確かめてもらう。パターン使用なら、**有給・欠勤の全日休暇は自動反映しない**（休みの変更の予定時刻と勤務日種別の入れ替えだけを自動にする。有給・欠勤は本人のスケジュール申請＋LINE からの申請の承認〔1-3 の PUT /requests〕を別に検討） |
| 既存のスケジュールを消してから登録 | 書き込む前に GET でその日のスケジュールを取り、保存（元に戻す用）。送る内容は、休暇以外の項目（出勤先所属・休憩など）を引き継いで組み立てる |
| 欠勤の表し方が会社の設定しだい | 休暇区分に「欠勤」があればそのコードの全日休暇。無ければ「欠勤は反映しない（出勤予定のまま、打刻が無い日として ToT が数える）」とし、承認は記録だけにする（決めてもらう） |
| 締め済みの日（資料に記載なし） | エラーの code・message をそのまま記録して「失敗」。グループに知らせて手で直してもらう |
| 利用禁止の時間帯・回数の上限 | VPS は禁止の時間帯は書き込まない（次の回に回す）。1件ずつ・1.1秒間隔。1回の反映は数件なので、上限（5分に500件）には遠い |

## 5. 仕組みの設計

### 5-1. 流れ

1. **フォーム送信**（alcoholCheckOnAttendanceForm。今の処理〔お知らせ停止・グループへの報告〕は変えない）
   - 区分が欠勤・有給休暇・休みの変更なら、新しいシート「TOT反映」に1行（受付番号 `S-YYYYMMDD-NNN`、状態「承認待ち」、合言葉）を足す
   - 勤怠管理グループへ、承認のカード（Flex）を送る：対象者・区分・日付・入力者・承認者・**反映する内容（予定）**、ボタン「承認してTOTに反映」「反映しない」
2. **ボタン**（勤怠管理グループの postback）
   - 問い合わせのボタンと同じ仕組みを使う：`AC_handleGroupEvent_` の postback → 新しい入口（例 `SCH_onGroupPostback_`）。データは `sch|1|approve|S-…|合言葉`（`inq|…` とは別。今の `INQ_parsePostback` は `inq|` 以外を無視するので共存できる）
   - 確かめること（INQ と同じ）：勤怠管理グループからか／押した人のLINE ID がとれるか／グループのメンバーか（INQ_memberName_）／同じイベントの2回目でないか（webhookEventId）／合言葉が合うか／ロック
   - 状態は一方向：承認待ち →（承認）反映待ち →（VPS）反映中 → 反映済み／失敗。承認待ち →（反映しない）反映しない。2回目以降のボタンは「○○さんが承認済みです」と返すだけ
   - **承認した人の記録**：「TOT反映」シートに承認者の名前（グループでの表示名）・LINE ID・日時。ToT の note（備考）にも「LINE承認：受付番号」を入れる（ToT 側でも追える。氏名は入れない）
3. **VPS の反映**（新しい cron。例：7:00〜23:00 の10分ごと。禁止の時間帯はとばす）
   - Apps Script の Webアプリへ `type: 'tot-write-queue'`（合言葉 TOT_SYNC_SECRET）で「反映待ち」を受け取る。受け取った行は Apps Script が「反映中」にする（同時に2回取りに来ても渡さない。30分たっても結果が来なければ「反映待ち」に戻す）
   - 1件ずつ：打刻の確認（GET timerecord）→ 今のスケジュールの取得と保存（GET daily-schedules）→ 既に目的の内容なら書かずに「反映済み」→ PUT → GET で確かめる
   - 結果を `type: 'tot-write-result'` で返す（受付番号・成功／失敗・エラーの code と message・反映前のスケジュール）。氏名は送らない（従業員識別キーと日付だけ）
4. **結果のお知らせ**：勤怠管理グループへ「11/12（木）の欠勤を ToT に反映しました（○○さん承認）」／失敗なら理由（打刻あり・パターン使用で非対応・API のエラー）と「本人にスケジュール申請を依頼します」。仕組みのエラー（VPS から結果が来ない等）は管理者へ（AC_adminNotice_・1日1回）

### 5-2. 二重に反映しない

- 受付番号ごとの状態が一方向に進む（反映済み・失敗・反映しない からは戻らない）。ボタンは合言葉＋webhookEventId で2回目を受け付けない
- VPS への受け渡しは「反映中」にしてから渡し、結果は受付番号で1回だけ受け付ける
- 書き込む前に今のスケジュールを読み、既に目的の内容なら PUT しない（PUT は同じ内容で上書きしても結果が同じなので、万一2回送っても壊れない）
- 同じ人・同じ日に「反映待ち」が2つあれば、あとの受付だけを反映し、前のものは「置き換え」にする

### 5-3. 元に戻す

- 反映済みの通知に「元に戻す」ボタン（`sch|1|undo|S-…|合言葉`）。押すと保存しておいた反映前のスケジュールで PUT し直す（反映前に予定が無かった日は DELETE）
- 打刻がある日は戻せない（ToT がエラーにする）。そのときはグループに「ToT の管理画面で直してください」
- 戻した記録（押した人・日時・結果）も「TOT反映」シートに残す

### 5-4. 【勤怠の変更】の文の扱い（打刻のお知らせ E-40・E-42・E-78）

| TOT反映の状態 | 打刻のお知らせ |
|---|---|
| 承認待ち・反映しない・失敗 | 今までどおり【勤怠の変更】（本人にスケジュール申請を依頼） |
| 反映待ち・反映中 | その連絡の分は送らない（管理本部が反映するので、本人の申請は要らない） |
| 反映済み | 送らない（ToT のスケジュールが変わるので、多くはエラー勤務でもなくなる） |

- 実装は、AC_formSplit の「期間の全部の日が申請済み」と同じところで、「TOT反映」シートの状態も見る

### 5-5. シート「TOT反映」（従業員マスタのファイル）の列（案）

受付番号／状態／受付日時／社員番号／氏名（参考）／区分／対象日（開始〜終了）／変更後の休みの日／入力者／反映する内容（予定。日ごとの JSON）／合言葉／承認者／承認者のLINE ID／承認日時／反映日時／反映前のスケジュール（JSON）／結果・エラー／元に戻した人・日時

## 6. 書き込みは VPS か Apps Script か

| | VPS の中継（おすすめ） | Apps Script |
|---|---|---|
| ToT に届くか | **届く**（許可IP 133.167.110.249 のトークンがある） | **届かない**（送信元のIPが決まらず、許可IPに入れられない） |
| トークンの置き場所 | 今と同じ VPS の .env だけ（書き込みの権限を足すなら、同じトークンの連携希望項目を変えるか、書き込み用のトークンを別に発行） | スクリプトプロパティに置くことになり、編集者が読める |
| 禁止の時間帯 | cron が時間帯をとばす。ボタンを押すのは何時でもよく、反映が 10:00・18:30 以降になるだけ | トリガーで後回しにする必要がある |
| すぐ反映できるか | 最大10分待ち（cron の間隔しだい） | すぐ（ただし上のとおり届かない） |
| 変更の量 | 中継に「反映待ちを受け取る→書き込む→結果を返す」を足す。Apps Script は受け渡しの2つの type を足す | － |

- VPS は外から呼べない（Webサーバーを置いていない）ので、VPS から Apps Script へ取りに行く形にする（今の中継と同じ向き）
- 書き込みの権限を持つトークンは影響が大きいので、可能なら**書き込み用のトークンを別に**して、連携希望項目を「日別スケジュールデータ（書き込み）」と読み取りに必要なものだけにする

## 7. 実装の前に決める・確かめること

1. ToT：今のトークンの連携希望項目（書き込みがあるか）。無ければ書き込み用のトークンを発行（許可IP は VPS）
2. ToT：全日休暇の取得方法（パターン使用か）

### 9-4. 書き込みの内容（src/tot-write.js の planItem）

- 共通：書き込む前に、その人の対象の日のスケジュール（GET /daily-schedules）と打刻（GET /daily-workings/timerecord?employeeKeys=）を読み直す。過ぎた日・打刻のある日が1日でもあれば、全部を書かずに失敗（past・punched）。書いたあとにもう一度読んで確かめる（verify）
- 欠勤・有給休暇：出勤の予定がある日だけ、`{ fulltimeHoliday: { code: 3 または 1 }, workDayTypeCode: 今の勤務日種別, workPlaceDivisionCode: 今の出勤先, note: 今の備考＋「LINE承認：受付番号」 }` で PUT（予定時刻・休憩は消える）。休み（公休など）・予定の無い日は変えない（「変更しなかった日」）。全部がもう目的の休暇なら書かない
- 休みの変更（もともとの休みの日 A、変更後の休みの日 B）：A が全日休暇・B が出勤予定のときだけ入れ替える
  - A ← B の出勤先・出勤と退勤の予定・勤務開始と終了の刻限・休憩を、日付だけずらして（日をまたぐ退勤も同じだけずらす）。勤務日種別は B のもの
  - B ← A の全日休暇（休暇区分）と勤務日種別、出勤先は B のもの
  - もう入れ替わっている（A が出勤・B が休み）なら書かない。それ以外は失敗（cannotSwap）
- 元に戻す：保存した反映前のスケジュール（GET の形）を PUT の形にして書き戻す。反映前に予定が無かった日は DELETE。今と同じなら書かない
- 勤務日種別は名前 → コード（平日 1・法定休日 2・法定外休日 3）。読めなければ失敗（dayType）
- TOT のエラーは code と message だけを返す。途中の日で失敗したら、そこで止めて、書いた日（written）と反映前のスケジュールを返す
- 読み取りの失敗・禁止の時間帯：まだ書いていなければ結果を返さない（Apps Script が30分後にもう一度渡す）。8:20〜10:00・17:20〜18:30 は始めない
- 1回に10件まで。TOT へは1件ずつ1.1秒の間隔

### 9-5. 「TOT反映」シート（従業員マスタのファイル）

列：受付番号／状態／受付日時／社員番号／氏名／区分／開始日／終了日／変更後の休みの日／入力者／反映する内容（予定）／合言葉／承認者／承認者のLINE ID／承認日時／受け渡し日時／反映日時／反映前のスケジュール（JSON）／結果／元に戻した人／元に戻した人のLINE ID／元に戻した日時

- 「TOT反映の記録」シート：日時／受付番号／操作／結果／LINEユーザーID／イベント番号（ボタンの2回目の防止にも使う）
- 状態：承認待ち → 反映待ち → 反映中 → 反映済み／失敗、承認待ち → 反映しない、承認待ち → 承認済み（記録のみ）、反映済み → 元に戻す待ち → 元に戻し中 → 元に戻し済み／元に戻し失敗、受付のとき自動反映できない → 対象外、同じ人の日が重なる前の受付（承認待ち・反映待ち）→ 置き換え
- 【勤怠の変更】を送らない状態：反映待ち・反映中・反映済み・元に戻す待ち・元に戻し中（社員番号・区分・開始日・終了日／変更後の日で、フォームの回答と結びつける）

## 10. 版 2026-11-13d（本番未導入）

### 10-1. 調べたこと（API の資料の原文）

- 申請の承認・棄却 `PUT /requests/{requestKey}`：送る項目は `administratorKey`（**必須**・管理者識別キー）・`approve`（**必須**・true 承認／false 棄却）・`adminComment`（任意・管理者コメント）。棄却の理由は adminComment に入れる。
  - 「管理者識別キーで指定した管理者が対象の申請の承認フローに存在しない、または承認レベルが異なる場合にはエラー」。承認フローが何段階もある申請は、1回の承認で次の段階に進むだけ（応答の status は applying のまま）。
  - 応答：requestKey・status・currentFlow・flow・adminComment・lastModifiedAdministratorKey
- スケジュール申請の一覧 `GET /requests/schedules/{年月}`：date（対象日）・requestedDate（申請日）・employeeKey・requestKey・applicant・status（applying／rejected／approved）・currentFlow・message（申請メッセージ）・adminComment・requested（申請内容：予定時刻・休憩・holidaysObtained〔休暇区分のコードと名前〕・workDayTypeName・scheduleTypeName など）・current（今のスケジュール）。additionalFields で schedulePatternCode・schedulePatternName・flow（段階ごとの管理者識別キー）も取れる。**カードに出す項目はすべて取れる**。
  - 状態に「取り下げ」は無い。本人が取り下げた申請は一覧から消えるものとして扱う（未確認）。
- 管理者の一覧 `GET /administrators`（連携希望項目「管理者データ（読み取り）」）：code・key・name。今のトークンにこの項目が無ければ 403。

### 10-2. 決めたこと・作ったもの

- 承認に使う管理者は、VPS の .env の `TOT_APPROVER_KEY`（1人）。調べ方は `node --env-file=.env src/tot-write.js --admins`（画面に出すだけ）。その管理者が申請の今の段階の承認者にいなければ、何もせず失敗（approverNotInFlow）。TOT 上は、その管理者が承認・棄却したことになる（承認した人の名前は「TOT反映」シートと adminComment「LINE承認：受付番号」に残る）。
- 申請の内容は中継（src/tot-relay.js）が朝・夜に取るスケジュール申請（今月・前月）から探す。**中継を置き換えるまでは、カードの申請の行は「（内容は TOT でご確認ください）」になり、申請メッセージは出ない**（申請があることとボタン3つは出る）。カードを作るときのデータは最新の中継の時点のもの（それより後の申請はカードに出ない。VPS は書く前に読み直す）。翌月の日の申請は今の中継では取っていない。
- ［申請を承認する］：申請中なら PUT approve:true（adminComment「LINE承認：受付番号」）。スケジュールは書かない。「元に戻す」は出さない。
- ［申請を棄却してフォームの内容で反映］：スケジュールの計画（過ぎた日・打刻・入れ替え）を先に確かめ、書けるときだけ PUT approve:false（adminComment「勤怠変更フォームの内容で反映したため」）→ スケジュールを PUT。「元に戻す」はスケジュールを書いたときだけ（棄却は戻せない）。
- 申請がもう申請中でない（承認・棄却・一覧に無い）→ 何もしない（requestGone）。グループに「何もしませんでした」。
- 本人のボタンの拒否・承認待ちのまとめ（A-49）・前日の15時台の再通知（A-50）・本人へのお知らせ（E-79・ATT-11）は gas/TotSync.gs の冒頭の説明のとおり。
- 「TOT反映」シートに列を5つ足した（やり方・本人の申請・申請の結果・本人へのお知らせ・再通知日時）。13c で作ったシートには見出しを自動で足す（今の値は変えない）。
- お知らせ設定に ATT-11 を末尾に足した。今の「お知らせ設定」「所属別お知らせ設定」には、見出しと所属の初期値（ON）のチェックボックスを末尾に自動で足す。
