7. **この Mac には Node.js が入っていないため、自動テスト（npm test）をここでは実行できません。** 実装の前に導入するか、別の場所で実行する必要があります（「7. テスト計画」）。

### 用語の説明
- **Webアプリ／デプロイ／版（バージョン）**：Apps Script をインターネットから呼べるようにする仕組みです。「デプロイ」すると、その時点のコードの写しが「版」として固定されます。LINEからの受信は、この固定された写しで動きます。
- **doPost**：Webアプリに外から送られたデータを受け取る、入口の関数です。
- **Webhook**：LINEが、届いたメッセージをこちらのURLへ自動で送る仕組みです。
- **postback（ポストバック）**：ボタンを押したときに、画面には文字を出さずに、決めておいた合図（データ）だけをこちらへ送る仕組みです。
- **Cloudflare Workers**：インターネット上で小さなプログラムを動かすサービスです。ここでは、LINEからの受信が本物か確かめてから Apps Script へ渡す「中継役」に使います。
- **署名検証**：LINEが受信データに付けている「改ざん防止の印」を確かめることです。Apps Script ではこの印を読めないため、Workers で確かめます。

### 2-3. 問い合わせのイベントの流し方（案）
| イベント | 今（LINE → Apps Script に直接） | Workers に切り替えた後 |

Workers を切り替えるときに、あわせて行うとよいこと（別途の承認で）：
1. 社員管理AIへの転送を「文字のメッセージ」と「`ea|` で始まる postback」だけに絞る。問い合わせの postback が社員管理AIに無駄に届かないようにするためです。

   - この印が無くても「5. 送信者の実在確認・ボタンの合言葉」で安全を保てるようにします。印は追加の守りです。

## 3. 社員管理AIとの衝突（勤怠管理グループ）

### 3-1. 今の勤怠管理グループに流れるもの
| 送るもの | 種類 | 扱う処理 |
|---|---|---|
| 「部門登録 ○○」 | 文字のメッセージ | 既存（部門登録） |
| 「入社」「退社」「取消」、【入社】【退社】【退職】【取消】… | 文字のメッセージ | 社員管理AI |
| 「承認 EA-YYYYMMDD-NNN 123456」「却下 EA-…」（クイックリプライのボタンで文字を送る） | 文字のメッセージ | 社員管理AI |
| 勤怠連絡フォームの報告など | こちらからの送信のみ | — |

- 社員管理AIは**postback を使っていません**（ボタンは押すと文字を送る「クイックリプライ」）。
- 既存の処理は、グループでは「部門登録」以外の文字に反応しません。社員管理AIは、文字のメッセージで決まった形のものだけを扱います。

### 3-2. 衝突しない設計（提案）
1. **問い合わせのボタンは postback にする**（文字を送らない）。文字のメッセージの扱いとはぶつかりません。
2. **postback の中身の先頭で、どの機能のものかを決める**（名前の決まり）
   - 問い合わせ：`inq|1|<操作>|<案件番号>|<合言葉>` 例 `inq|1|take|Q-20261105-003|k7f2m9`
     - `1` は形式の版。操作は `take`（対応します）・`done`（対応済みにする）
     - 合言葉は案件ごとに作る、推測できない短い文字列（「5. ボタン」で使う）
   - 社員管理AIが将来 postback を使うとき：`ea|…`
   - 既存の機能が将来使うとき：`ac|…`
   - どれにも当たらない postback は、どの処理も何もしない
   - LINE の postback の中身は300文字までです。上の形は40文字程度です。
3. **ボタンを押したときに画面に出る文字（displayText）は、ほかの処理が反応する形にしない**
   - 例：「対応します（Q-20261105-003）」。「入社」「部門登録」などで始めない。
   - displayText は画面に出るだけで、文字のメッセージとしては届きません。念のための決まりです。
4. **案件番号の形を分ける**：問い合わせは `Q-YYYYMMDD-NNN`、社員管理AIは `EA-YYYYMMDD-NNN`。
5. **返信は「返信（reply）」を使う**：ボタンを押した結果は、そのイベントの返信用の番号で返します。返信は送信数に数えられず、ほかの処理の返信と取り違えることもありません。
6. 社員管理AIは同じグループで「申請者が今もメンバーか」を確認しています。問い合わせのボタンでも同じ確認（`/v2/bot/group/{グループ}/member/{利用者}`）をします。

## 5. 重複受信・送信者の実在確認・ボタンの二重押し

### 5-1. 重複受信の対策
同じメッセージが2回届く原因：
- Workers の再送（最長24時間）
- LINE の再送機能（今はオフ。オンにすると、届いたものに `deliveryContext.isRedelivery: true` が付く）
- 同じ送信の中に、同じイベントが2回入ること

対策（二重に守る）：
1. `webhookEventId` を Apps Script の一時記憶（CacheService、最長6時間）に入れ、見たことがあれば処理しない。素早く判定するためです。
2. 一時記憶は6時間で消えるため、問い合わせのシートにも `webhookEventId` とメッセージの番号（`message.id`）を書きます。追記の前に、同じ番号がすでにないかを確かめます（直近の行だけを見る）。
3. 書き込みは、既存と同じスクリプトの鍵（`LockService.getScriptLock()`）の中で行います。同時に届いた2つの処理が同じ案件を作らないようにするためです。

### 5-2. 送信者の実在確認（プロフィール取得）
- 1対1：`GET /v2/bot/profile/{利用者ID}` でLINE表示名を取ります（既存の `AC_fetchDisplayName_` と同じ）。
  - 取れない（友だちでない・ブロック中・偽のデータ）ときは案件にせず、「受信記録」に「実在確認できず」と残すだけにします。
  - 偽のデータで案件が作られるのを防げます。
- グループのボタン：`GET /v2/bot/group/{グループ}/member/{利用者}` で、押した人が今もメンバーかを確かめます（社員管理AIと同じ）。メンバーでなければ何も変えずに返信だけします。
- パソコン版のLINEでは送信者のIDが付かないことがあります（社員管理AIの資料より）。IDが無いボタン操作は受け付けず、「スマートフォンのLINEから押してください」と返信します。
- 従業員との紐付けは、従業員マスタで **LINEユーザーIDが一致し、かつ「LINE確認済み」にチェックがある行だけ**にします。氏名や表示名から推測しません。
  - IDが入っていてもチェックが無い人：「確認待ち（LINE表示名）」と表示します。登録の案内は送りません（登録は済んでいるため）。

### 5-3. ボタンの二重押し・古いボタン
- 案件の状態は「未対応 → 対応中 → 対応済み」の一方向だけにします。
- 押されたときは、必ずシートの今の状態を読み直して判断します（ボタンに書かれた状態は使いません）。

| 今の状態 | 「対応します」 | 「対応済みにする」 |
|---|---|---|
| 未対応 | 対応中にする（担当＝押した人） | 対応済みにする |
| 対応中 | 変えない。「○○さんが対応中です」と返信 | 対応済みにする |
| 対応済み | 変えない。「対応済みです（○日○時・○○さん）」と返信 | 変えない。同じ返信 |

- ボタンの合言葉が案件と合わないときは、何も変えず「このボタンは使えません」と返信します。古い通知や作り直した案件のボタンが該当します。
- 同じボタンを2回押した場合も、2回目は上の表の「変えない」になります。
- 返信はすべて reply（送信数に数えない）です。

## 6. 送信数の見込み
- LINE では、**グループへ1通送ると、グループの人数（公式アカウントを除く）分として数えられます。** 返信（reply）は数えられません。
- 勤怠管理グループの人数は GitHub からは分かりません。下の表では**5人と仮定**しています（管理本部の在籍者は4人：10/22 の部署別表示より）。

| 送るもの | 送り方 | 1回の通数 | 月の回数（仮定） | 月の通数（5人） |
|---|---|---|---|---|
| 新しい問い合わせの通知 | グループへ送信 | 5 | 30件 | 150 |
| リマインド（9:00・17:00、未対応・対応中があるときだけ、1回1通にまとめる） | グループへ送信 | 5 | 30〜60回 | 150〜300 |
| 対応中の案件への追記の通知（30分に1回まで） | グループへ送信 | 5 | 10回 | 50 |
| ボタンを押した結果 | 返信 | 0 | — | 0 |
| 未登録の人への社員番号の案内（1回だけ） | 返信 | 0 | — | 0 |
| **合計** | | | | **約350〜500** |

- 案件が0件のときはリマインドを送りません。上の表のリマインドの回数は、案件が残っている日の数で決まります。
- 今のプランは gas/SETUP.md によるとライト（月5,000通）の見込みです。既存の送信数は `alcoholCheckUsage` で確認できます（読み取りのみ）。既存の仕組み（`AC_checkLineQuota_`）が毎朝、80・95・100％で管理者に知らせます。
- 人数がN人なら、月の通数は「約70〜100 × N」です。

  - 定型連絡の判定（「退勤」「出勤しました」「遅刻します」→ 記録のみ。「遅刻の理由を相談したい」→ 案件）

  - 状態の移り方（上の表のすべての組み合わせ）、合言葉の照合、postback の読み取り（`inq|` 以外は無視）
  - リマインドの文面（「前日から継続」の表示、0件なら送らない）
  - 重複の判定（webhookEventId・message.id）
- 結合テスト（Apps Script の模擬環境）
  - `feature/employee-admin` と `feature/self-request-notice` にある `test/helpers/gas-mock.js`（シートはメモリ上、LINEなどの通信は記録するだけで送らない）を使います。
  - 既存の「コード.gs」と `Inquiry.gs` を同じ環境で読み込み、次を確かめます。
    - 社員番号の登録・部門登録・友だち追加・ToTの取り込みが今までどおり動くこと
    - 問い合わせの受付・追記・ボタン・リマインド・重複受信・偽のボタン
    - `INQ_MODE` が未設定のとき、何も起きないこと
- 既存のテスト（main で81件、PR #1 のブランチで103件）がすべて成功すること。

### 7-2. 本番に影響しないテスト
1. **テスト用の Apps Script とスプレッドシート**（架空データ）
   - 勤怠連絡フォームの部署別のときと同じやり方です。
   - LINE の送信はせず、「送るはずだった内容」をシートに記録するモードで動かします。
   - ボタンの postback は、作ったイベントのデータを関数に直接渡して確かめます。
2. **本番の「記録のみ」モード**（`INQ_MODE=record`）
   - 新しい版の発行後に、受付と履歴の保存だけを行います。グループへは送りません。
   - 数日、実際のメッセージで、案件の分け方・定型連絡・機密の判定が正しいかを確かめます。
3. **管理者だけでの試験**（`INQ_MODE=on`、通知先を管理者の個別LINEにする設定）
   - 実際のボタンの動きを確かめてから、勤怠管理グループへ切り替えます。
4. 段階の切り替えと停止は、スクリプトプロパティ `INQ_MODE` だけで行います（`off` / `record` / `on`）。止めるときは `off` にするか、`INQ_stop` を実行します。
